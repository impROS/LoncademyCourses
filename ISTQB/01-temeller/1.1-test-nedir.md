# 1.1 — Test Nedir? Hedefler ve Debugging

> **Süre:** ~20 dakika okuma + 10 dakika pratik
> **Test:** [`1.1-test.html`](1.1-test.html) · 13 soru

---

## Neden bu konu

Sınav ilk sorularından itibaren senin "test" kelimesini **ISTQB'nin anladığı gibi** anlayıp anlamadığını
yoklar. Günlük hayatta "test etmek" = "çalışıyor mu bakmak". ISTQB'de test bunun çok ötesinde:
planlama, analiz, tasarım, raporlama dahil bir **süreç**. Ve en sık düşülen tuzak: **test ile debugging'i
aynı şey sanmak.**

**Büyük fikir:** Test **kusuru bulur**, debugging **kusuru düzeltir**. Biri arıza arar, diğeri sebebi bulup
onarır. Sınav bu ayrımı defalarca sorar.

---

## 1. Test nedir?

Test, bir iş ürününün (work product) **kalitesini değerlendirmek** ve **kusurları bulmak** için yapılan
tüm aktiviteleri kapsar.

İki büyük yanlış anlama var, ikisini de düzelt:

| Yaygın sanı | ISTQB gerçeği |
|---|---|
| "Test = yazılımı çalıştırmak" | Test hem **dinamik** (çalıştırarak) hem **statik** (çalıştırmadan — inceleme, review) olabilir |
| "Test = sadece test yürütme" | Test yürütme, testin **sadece bir aktivitesidir**. Planlama, analiz, tasarım, izleme, raporlama da testtir |

> ⚠️ **Tuzak:** `Which of the following is a testing activity?` sorusunda `test execution` doğru görünür
> ama şıklarda `test planning` de varsa ve soru "Choose TWO" diyorsa ikisi de doğrudur. Test yürütmeye
> indirgeme.

**Statik / dinamik ayrımı** (Bölüm 3 ve 4'te derinleşecek):

| | **Statik test** | **Dinamik test** |
|---|---|---|
| Kod çalışıyor mu | Hayır | Evet |
| Neyi bulur | **Kusuru doğrudan** (kodda/belgede) | **Arızayı** — kusuru dolaylı |
| Örnek | Review, inspection, statik analiz | Birim testi, sistem testi |
| Ne zaman | Çok erken — kod olmadan da | Çalıştırılabilir bir şey olduğunda |

## 2. Test hedefleri (test objectives) ⭐

Müfredatın saydığı tipik test hedefleri:

| Hedef | Ne demek |
|---|---|
| **Kusurları ve arızaları bulmak** | En bilinen hedef — ama tek hedef değil |
| İş ürününü **değerlendirmek** (requirement, user story, design, code) | Statik testin ana işi |
| Gereksinimlerin **karşılandığını doğrulamak** (verification) | "Şartnameye uygun mu?" |
| Test nesnesinin **kullanıcı beklentisini karşıladığını doğrulamak** (validation) | "Kullanıcının istediği bu muydu?" |
| Kalite düzeyine **güven** oluşturmak | Kusur bulamamak da bilgidir |
| **Risk seviyesini düşürmek** | Bölüm 5'in kalbi |
| Karar vericilere **bilgi sağlamak** | Test raporunun amacı |
| Yasal/sözleşmesel/standart **uyumluluğu** karşılamak | Regüle sektörlerde |

> ⚠️ **Tuzak:** "The objective of testing is to prove the software is correct" **yanlıştır.**
> Test doğruluğu **kanıtlayamaz** (1.3'teki ilk prensip). Doğru ifade "to provide confidence" veya
> "to reduce risk"tir. `prove`, `guarantee`, `ensure defect-free` gören şıkları ele.

**Hedefler bağlama göre değişir.** Aynı ekip:
- **Birim testinde** → kusurları erken bulup **hızlıca düzeltmek**
- **Kabul testinde** → sistemin beklendiği gibi çalıştığını **teyit etmek ve güven vermek**
- **Bakım/regresyon testinde** → değişikliğin **yeni kusur getirmediğini** göstermek

hedefini güder. Aynı aktivite, farklı amaç.

---

## 3. Verification ile Validation ⭐

Bu ikili neredeyse her denemede çıkar.

| | **Verification (doğrulama)** | **Validation (geçerleme)** |
|---|---|---|
| Sorusu | *"Are we building the product **right**?"* | *"Are we building the **right** product?"* |
| Referansı | **Şartname / spesifikasyon** | **Kullanıcı ihtiyacı / kullanım amacı** |
| Tipik örnek | Kod, tasarım dokümanına uyuyor mu | Kullanıcı bu ekranla işini yapabiliyor mu |
| Tipik seviye | Birim, entegrasyon, sistem | **Kabul testi (UAT)** |

**Hafıza kancası:** ver**i**fication → spec**i**fication (ikisinde de "i"). vali**da**tion → kullanıcı "**evet, da** budur" der.

> ⚠️ **Tuzak:** Bir sistem verification'ı geçip validation'da kalabilir: şartnameye **birebir** uyuyordur
> ama şartnamenin kendisi kullanıcının istediği şey değildir.

## 4. Test ve Debugging — en kritik ayrım ⭐⭐

| | **Testing** | **Debugging** |
|---|---|---|
| Amacı | **Arıza (failure) bulmak** / kaliteyi değerlendirmek | Arızanın **sebebini bulup düzeltmek** |
| Kim yapar (tipik) | Tester (veya geliştirici) | **Geliştirici** |
| Ne üretir | Kusur raporu, test sonucu | Düzeltilmiş kod |
| Testin kapsamında mı | Evet | **Hayır — debugging bir test aktivitesi değildir** |

**Debugging'in üç adımı** (bu sıra sorulabilir):

1. **Reproduction** — arızayı yeniden üret
2. **Diagnosis** — kök nedeni (kusuru) teşhis et
3. **Fixing** — kusuru düzelt

Düzeltmeden sonra ne olur? **Test devreye tekrar girer:**

- **Confirmation testing** → düzeltme gerçekten işe yaramış mı? (aynı testi tekrar koş)
- **Regression testing** → düzeltme başka bir yeri bozmuş mu?

> ⚠️ **Tuzak:** `Who is responsible for debugging?` → **developer**. `Who is responsible for confirmation
> testing?` → **tester** (düzeltmeyi doğrulamak testtir). Sınav bu ikisini yan yana sorar.

**Statik testte durum farklı:** Statik test **kusuru doğrudan** bulur (kodun içindeki hatalı satırı
gözünle görürsün), arızayı değil. Bu yüzden statik testten sonra **debugging gerekmez** — teşhise gerek
yok, kusur zaten elinde.

| | Dinamik testten sonra | Statik testten sonra |
|---|---|---|
| Bulunan | **Failure** (belirti) | **Defect** (doğrudan) |
| Debugging gerekir mi | **Evet** — sebebi bulmak lazım | **Hayır** |

## Sık karıştırılanlar — tek tabloda

| Soruda/pratikte geçen | Doğru cevap | Neden diğeri değil |
|---|---|---|
| "Find the cause of the failure and fix it" | **Debugging** | Testing sebebi aramaz, belirtiyi bulur |
| "Check that the fix works" | **Confirmation testing** (test) | Debugging düzeltmeyi yapar, doğrulamaz |
| "Does it meet the specification?" | **Verification** | Validation kullanıcı ihtiyacına bakar |
| "Does it meet the user's needs?" | **Validation** | Verification şartnameye bakar |
| "Testing proves there are no defects" | **Yanlış ifade** | Test yokluğu kanıtlayamaz — sadece varlığı gösterir |
| Statik testte bulunan şey | **Defect** | Failure için kodun çalışması gerekir |
| Dinamik testte doğrudan gözlenen şey | **Failure** | Defect'i çıkarım yoluyla bulursun |
| "Test = test execution" | **Yanlış** | Yürütme, testin bir aktivitesi; planlama/analiz/tasarım da test |

## 🖥 Pratik — Hedef ve rol ayırma egzersizi

> **Amaç:** Bir cümle görünce "bu test mi, debugging mi" refleksini kazanmak · **Süre:** 10 dk
> **💸 Maliyet:** Yok — kalem kâğıt.

### Adımlar

1. Bir kâğıda iki sütun çiz: **TESTING** ve **DEBUGGING**.
2. Aşağıdaki 8 cümleyi doğru sütuna yaz. Yanına parantez içinde **kim yapar** yaz.

   a. The tester runs the login scenario and the page returns HTTP 500.
   b. The developer sets a breakpoint and steps through `AuthService.login()`.
   c. The team reviews the user story and notices a missing acceptance criterion.
   d. After the fix, the same login scenario is executed again and passes.
   e. The developer changes line 42 from `>` to `>=`.
   f. A suite of 200 unrelated tests is run to see if the fix broke anything.
   g. The test manager writes a report saying 12 of 40 high-risk tests failed.
   h. The developer reproduces the crash on a local machine before investigating.

3. Sonra her satırın yanına, **statik mi dinamik mi** olduğunu yaz (uygulanabiliyorsa).

**Çözüm anahtarı:**

| | Sütun | Kim | Not |
|---|---|---|---|
| a | TESTING (dinamik) | Tester | Gözlenen şey bir **failure** |
| b | DEBUGGING | Developer | Diagnosis adımı |
| c | TESTING (**statik**) | Ekip | Doğrudan **defect** bulundu, debugging gerekmez |
| d | TESTING — **confirmation testing** | Tester | Düzeltmeyi doğrulamak testtir |
| e | DEBUGGING | Developer | Fixing adımı |
| f | TESTING — **regression testing** | Tester | Yan etki arıyor |
| g | TESTING | Test manager | Karar vericiye **bilgi sağlama** hedefi |
| h | DEBUGGING | Developer | Reproduction adımı |

- [ ] **Kontrol:** 8 satırın en az 7'sini doğru yerleştirdin.
- [ ] **Kaydet:** Yanlış yaptığın satır(lar): ______ → o satırın açıklamasını tekrar oku.

## Sınavda nasıl karşına çıkar — örnek kalıplar

**Kalıp 1 — Test vs debugging rolü**
> *"A tester reports that the application crashes when an empty password is submitted. A developer
> reproduces the crash, identifies the null check is missing, and adds it. Which activity did the
> **developer** perform?"* → **Debugging**

**Kalıp 2 — Hedefin mutlak ifadeyle bozulması**
> *"Which of the following is a valid objective of testing?"*
> Şıklarda `To prove that the software has no defects` varsa → **eleyin**. Doğru şık
> `To reduce the level of risk of inadequate software quality` gibi olur.

**Kalıp 3 — Verification / validation**
> *"The acceptance test confirms that the system supports the business process the users actually
> follow. This is an example of:"* → **Validation**

**Kalıp 4 — Statik testten sonra debugging**
> *"A code review identifies an incorrect boundary condition in a method. What must happen next?"*
> → Kusur **doğrudan** bulunduğu için teşhise gerek yok; düzeltilir. Debugging'in *diagnosis*
> adımı gerekmez.

**Kalıp 5 — Test ≠ yürütme**
> *"Which of the following are test activities? (Choose TWO.)"* → `test planning` ve `test analysis`
> gibi şıklar, `debugging` çeldiricisiyle birlikte gelir.

## 60 saniyelik özet

- Test = kaliteyi değerlendirmek + kusur bulmak. **Yürütmeden ibaret değil**; planlama, analiz, tasarım, raporlama da test.
- Test **statik** (çalıştırmadan) veya **dinamik** (çalıştırarak) olabilir.
- **Statik test → defect'i doğrudan bulur.** **Dinamik test → failure'ı gözler.**
- Hedefler: kusur bulmak, iş ürününü değerlendirmek, verification, validation, **güven vermek**, **riski azaltmak**, bilgi sağlamak, uyumluluk.
- Test doğruluğu **kanıtlayamaz** — `prove` / `guarantee` / `defect-free` içeren şık yanlıştır.
- **Verification** = şartnameye uygun mu. **Validation** = kullanıcının ihtiyacı bu mu.
- **Debugging bir test aktivitesi değildir.** Adımları: **reproduction → diagnosis → fixing**. Geliştirici yapar.
- Düzeltmeden sonra: **confirmation testing** (düzeltme çalıştı mı) + **regression testing** (başka yeri bozdu mu).
