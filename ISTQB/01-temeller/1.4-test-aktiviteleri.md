## Neden bu konu

1.1'de "test yürütmeden ibaret değildir" dedik; bu dosya o cümlenin karşılığıdır. Sınav senden
**hangi aktivitede hangi iş ürününün üretildiğini** ve **hangi rolün ne yaptığını** bilmeni ister.
En sık kaybedilen puan: bir testware'i yanlış aktiviteye bağlamak (test case'i "test yürütme"de
üretildiğini sanmak gibi) ve test manager ile tester sorumluluklarını karıştırmak.

**Büyük fikir:** Test bir **aktiviteler kümesidir**; her aktivite bir **testware** üretir ve bu testware'ler
test tabanına **izlenebilir** şekilde bağlıdır.

## 1. Test aktiviteleri ve görevleri ⭐

Müfredat yedi aktivite grubu tanımlar. **Sıralı değil** — birbirine paralel veya iteratif olabilir,
ama mantıksal bir akışları vardır.

| # | Aktivite | Ne yapılır | Ürettiği testware |
|---|---|---|---|
| 1 | **Test planning** | Hedefleri tanımla, yaklaşımı seç, kaynakları/programı belirle | **Test plan** |
| 2 | **Test monitoring & control** | İlerlemeyi ölç, plandan sapmayı düzelt | Test progress reports, **test control** kararları |
| 3 | **Test analysis** | Test tabanını incele, **neyi test edeceğini** belirle | **Test conditions**, kusur raporları (statik bulgular) |
| 4 | **Test design** | **Nasıl test edeceğini** belirle | **Test cases**, test charters, coverage items, test data gereksinimleri |
| 5 | **Test implementation** | Yürütmeye hazır hale getir | **Test procedures**, test suites, test data, test scripts, test ortamı |
| 6 | **Test execution** | Testleri koş, sonuçları karşılaştır | Test **results**, test logs, **defect reports** |
| 7 | **Test completion** | Kapanış: öğrenilenleri topla, testware'i arşivle | **Test completion report**, action items, arşivlenmiş testware |

### 3 ile 4 arasındaki fark — en kritik ayrım ⭐

| | **Test analysis** | **Test design** |
|---|---|---|
| Sorusu | **WHAT to test** — ne test edilecek | **HOW to test** — nasıl test edilecek |
| Girdi | Test basis (gereksinim, user story, kod, risk) | Test conditions |
| Çıktı | **Test conditions** | **Test cases** (+ coverage items, test data) |
| Örnek | "Kargo ücreti sınırı test edilmeli" | "total=499 → ücret var, total=500 → ücret yok" |

**Hafıza kancası:** analiz**A** = n**A**sıl değil, **NE**. desig**N** = **N**asıl.

> ⚠️ **Tuzak:** Test analysis aynı zamanda **statik test** yapar — test tabanındaki kusurları
> (belirsizlik, eksiklik, çelişki) bulur. Bu yüzden test analysis'in çıktısı arasında **kusur raporları** da vardır.

### 5 ile 4 arasındaki fark

Test design **test case'i yazar**; test implementation onu **koşulabilir hale getirir**:
test verisini hazırlar, test ortamını kurar, prosedürleri sıraya dizer, otomasyon script'ini yazar.

## 2. Test process in context

Test süreci **her projede aynı değildir**. Şu faktörler süreci şekillendirir:

- Paydaşlar (ihtiyaçlar, beklentiler, işbirliği düzeyi)
- Ekip (beceriler, deneyim, bilgi seviyesi)
- İş alanı (kritiklik, risk, regülasyon, pazar ihtiyaçları)
- Teknik faktörler (yazılım tipi, mimari, teknoloji)
- Proje kısıtları (kapsam, zaman, bütçe, kaynak)
- Organizasyonel faktörler (yapı, politikalar, uygulamalar)
- **Yazılım geliştirme yaşam döngüsü** (yöntemler, pratikler)
- Araçlar (kullanılabilirlik, kullanılabilirliği, uyumluluk)

Bu liste 1.3'teki **prensip 6 (context dependent)** ile birebir bağlantılıdır.

## 3. Testware — test aktivitelerinin ürünleri ⭐

**Testware = test aktivitelerinin ürettiği tüm iş ürünleri.**

| Aktivite | Ürettiği testware |
|---|---|
| Test planning | Test plan, test programı, risk kaydı, **entry/exit criteria** |
| Test monitoring & control | Test progress reports, dokümante edilmiş kontrol yönergeleri, risk bilgileri |
| Test analysis | (Önceliklendirilmiş) **test conditions**, statik testte bulunan kusur raporları |
| Test design | (Önceliklendirilmiş) **test cases**, test charters, coverage items, **test data requirements**, test ortamı gereksinimleri |
| Test implementation | **Test procedures**, otomasyon test script'leri, test suites, test data, test execution schedule |
| Test execution | Test logs, **defect reports** |
| Test completion | **Test completion report**, iyileştirme için action items, dokümante edilmiş değişiklik talepleri, **finalize edilmiş test varlıkları** |

> ⚠️ **Tuzak:** `defect report` iki yerde üretilir: **test analysis** (statik test bulguları) ve
> **test execution** (dinamik test bulguları). Şıklarda ikisi de doğruysa soruyu dikkatli oku.

## 4. İzlenebilirlik (traceability) ⭐

Testware'in **test tabanına (test basis)** geriye doğru bağlı olması.

**Test basis:** testin dayandığı her şey — gereksinimler, user story'ler, kabul kriterleri, tasarım,
kod, risk kaydı, standartlar.

**İzlenebilirlik zinciri:**

```
Test basis (gereksinim / risk)
   ↓
Test condition (analysis)
   ↓
Test case (design)
   ↓
Test procedure (implementation)
   ↓
Test result + defect report (execution)
```

**İzlenebilirlik ne sağlar:**

| Fayda | Nasıl |
|---|---|
| **Etki analizi** (impact analysis) | Bir gereksinim değişirse hangi testler etkilenir, anında görürsün |
| **Kapsam ölçümü** (coverage) | Gereksinimlerin yüzde kaçı test edilmiş? |
| **Denetlenebilirlik** (auditability) | Regüle sektörlerde kanıt |
| **IT yönetişimi** | Kararların gerekçelendirilmesi |
| **Test ilerlemesini/durumunu raporlama** | Teknik olmayan paydaşa anlaşılır rapor |
| **Test sürecinin iş hedefleriyle ilişkilendirilmesi** | "Bu test hangi iş riskini kapatıyor?" |

**Hafıza kancası:** İzlenebilirlik = **"neden bu testi koşuyoruz?"** sorusunun kâğıt üstündeki cevabı.

## 5. Test rolleri ⭐

Müfredat **iki** ana rol tanımlar.

| | **Test management role** | **Testing role** |
|---|---|---|
| Kim | Test manager, test lead | Tester, test analyst, test engineer, test automation engineer |
| Sorumluluk | **Genel test süreci**, ekip liderliği | **Teknik test işi** |
| Ne yapar | Test planlama, izleme, kontrol, tamamlama; kaynak ve program yönetimi; raporlama | Test analizi, tasarım, implementation, yürütme; kusur raporlama |
| Odak | **Yönetim** | **Uygulama** |

**Kritik notlar:**

- Bu roller **kişi değil, rol**dür. **Aynı kişi ikisini de üstlenebilir**; roller zaman içinde değişebilir.
- Küçük/çevik ekiplerde test yönetimi sorumluluğu **takım liderine, ürün sahibine veya ekibin kendisine**
  dağıtılabilir. ⚠️ Bu madde sınavda çıkar: "test manager olmadan test yönetimi yapılamaz" **yanlıştır**.
- Ekip dışı destek (test otomasyon uzmanı, performans uzmanı) alınabilir.

## Sık karıştırılanlar — tek tabloda

| Soruda/pratikte geçen | Doğru cevap | Neden diğeri değil |
|---|---|---|
| "Determine WHAT to test" | **Test analysis** | Design nasıl test edileceğini belirler |
| "Determine HOW to test" | **Test design** | Analysis neyi test edeceğini belirler |
| Test **conditions** üretilir | **Test analysis** | Test case'ler design'da üretilir |
| Test **cases** üretilir | **Test design** | Implementation onları koşulabilir yapar |
| Test **data** hazırlanır, ortam kurulur | **Test implementation** | Design sadece veri *gereksinimini* belirler |
| **Defect report** üretilir | **Test execution** (ve statik testte **test analysis**) | Test design kusur raporu üretmez |
| **Test completion report** | **Test completion** | Test progress report monitoring'de üretilir |
| Bir gereksinim değişti, etkilenen testleri bul | **Traceability / impact analysis** | Coverage ölçüm, etki değil |
| Kaynak ve program yönetimi | **Test management role** | Testing role teknik işi yapar |
| Test case yazmak | **Testing role** | Test manager süreci yönetir |
| "There must always be a dedicated test manager" | **Yanlış** | Sorumluluk ekibe/ürün sahibine dağıtılabilir |

## 🖥 Pratik — Jira/Xray ile izlenebilirlik zinciri kurma

> **Amaç:** Gereksinim → test case → yürütme → kusur zincirini gerçekten kurmak · **Süre:** 15 dk
> **💸 Maliyet:** Xray **30 günlük deneme** ile gelir. Kurulum yaptıysan bitince kaldır (bkz. temizlik).
> Xray kurmadıysan **alternatif adım 6'da**.

### Adımlar (Jira + Xray)

1. Jira'da `ISTQB Lab` projesine gir. **Create** → issue type **Story**.
   **Summary:** `Kargo ücreti 500 TL ve uzerinde ucretsiz olmali`. Kaydet, anahtarını not et (ör. `ISTQB-1`).
2. **Create** → issue type **Test**.
   **Summary:** `500 TL siniri - sinir degerleri`
   **Test Type:** `Manual`
   Steps kısmına üç adım gir:
   - `Sepet toplamini 499 yap` → Expected: `Kargo ucreti tahsil edilir`
   - `Sepet toplamini 500 yap` → Expected: `Kargo ucreti tahsil edilmez`
   - `Sepet toplamini 501 yap` → Expected: `Kargo ucreti tahsil edilmez`
   Kaydet.
3. Test issue'sunda **Link** → ilişki tipi **tests** → `ISTQB-1` seç.
   **Bu link izlenebilirlik zincirinin ilk halkasıdır.**
4. **Create** → issue type **Test Execution**. Summary: `Sprint 1 - kargo testleri`.
   İçine adım 2'deki testi ekle. Testi çalıştır ve **500** adımını `FAIL` işaretle.
5. FAIL satırından **Create defect** de. Summary: `500 TL tam sinirda kargo ucreti tahsil ediliyor`.

- [ ] **Kontrol:** `ISTQB-1` story'sini aç. Sağdaki panelde/link bölümünde **hem test hem defect**
      zincir üzerinden görünür olmalı. Bu, **impact analysis**'i mümkün kılan şeydir.
- [ ] **Kaydet:** Zincirdeki beş halkayı kendi issue anahtarlarınla yaz:
      basis ______ → condition ______ → case ______ → execution ______ → defect ______

### Adım 6 — alternatif (araçsız, kâğıt/metin dosyası)

Xray kurmadıysan aynı zinciri bir metin dosyasında kur:

```bash
cat > ~/istqb-lab/traceability-lab.md <<'EOT'
| Test basis | Test condition | Test case | Result | Defect |
|---|---|---|---|---|
| REQ-1 Kargo 500+ ucretsiz | Sinir davranisi 500 | TC-1 total=499 | PASS | - |
| REQ-1 | Sinir davranisi 500 | TC-2 total=500 | FAIL | DEF-1 |
| REQ-1 | Sinir davranisi 500 | TC-3 total=501 | PASS | - |
EOT
```

- [ ] **Kontrol:** Tabloda her satır bir gereksinime kadar geri sürülebiliyor.
- [ ] **Kaydet:** REQ-1 değişirse kaç test case'i güncellemen gerekir? ______

## Sınavda nasıl karşına çıkar — örnek kalıplar

**Kalıp 1 — Aktivite ↔ testware eşleme**
> *"During which test activity are test conditions produced?"* → **Test analysis**

**Kalıp 2 — Analysis / design ayrımı**
> *"The team decides that the discount boundary must be tested, but has not yet decided which values
> to use. Which activity has been completed?"* → **Test analysis** (WHAT belirlendi, HOW belirlenmedi)

**Kalıp 3 — İzlenebilirliğin faydası**
> *"A requirement is changed late in the project. Which benefit of traceability helps the team decide
> which tests must be updated?"* → **Impact analysis**

**Kalıp 4 — Rol sorumluluğu**
> *"Who is typically responsible for scheduling test resources and reporting test progress to
> stakeholders?"* → **The test management role**

**Kalıp 5 — Rolün esnekliği**
> *"In an Agile team without a dedicated test manager, who can take on test management
> responsibilities?"* → **A team lead, the product owner, or the team itself.**

**Kalıp 6 — Implementation'ı ayırt etme**
> *"Preparing test data and setting up the test environment belongs to which activity?"*
> → **Test implementation**

## 60 saniyelik özet

- Yedi aktivite: **planning · monitoring & control · analysis · design · implementation · execution · completion**.
- **Analysis = WHAT** → test conditions. **Design = HOW** → test cases. En sık sorulan ayrım.
- **Implementation** = koşulabilir hale getirme: test data, test procedure, ortam, script.
- **Execution** = koşma → test logs + **defect reports**. **Completion** = kapanış → **test completion report** + arşiv.
- Statik test yaptığı için **test analysis de kusur raporu üretebilir**.
- **Testware** = test aktivitelerinin ürettiği iş ürünlerinin tamamı.
- **Traceability**: test basis → condition → case → procedure → result. Faydaları: **impact analysis**, kapsam ölçümü, denetlenebilirlik, raporlama, iş hedefleriyle ilişkilendirme.
- İki rol: **test management** (süreç, kaynak, rapor) ve **testing** (analiz, tasarım, yürütme).
  Aynı kişi ikisini yapabilir; **ayrı bir test manager zorunlu değildir**.
