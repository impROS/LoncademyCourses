# 4.2 — Exception handling ve ProblemDetail

> **Alan:** Web katmanı — ⭐ API'ni kullanan kişinin seni sevip sevmeyeceğini belirleyen konu
> **Süre:** ~30 dakika okuma + 20 dakika pratik
> **Test:** [`4.2-test.html`](4.2-test.html) · 14 soru

---

## Neden bu konu

[4.1](4.1-request-mapping.md)'in sonunda bir soru bırakmıştım. Geçersiz bir istek attığımızda
gelen yanıt buydu — gerçek çıktı:

```json
{"timestamp":"2026-09-02T21:42:53.939Z","status":400,"error":"Bad Request","path":"/siparisler"}
```

Şimdi kendini bu API'yi kullanan mobil geliştiricinin yerine koy. Elinde şu bilgi var:
"bir şey yanlış". **Hangi alan?** Bilmiyor. **Neden?** Bilmiyor. **Kullanıcıya ne
göstereceğim?** Bilmiyor.

Sana bir mesaj yazar, sen günlüklere bakarsın, yarım saat gider. Her seferinde.

**Büyük fikir:** Bir hata yanıtı da bir **sözleşmedir**. İstemcinin makine olarak
okuyabileceği, tutarlı bir yapısı olmalı — ve bunun bir standardı var.

---

## 1. Standart: RFC 9457 ve `ProblemDetail` ⭐

HTTP hata gövdeleri için bir standart var (RFC 9457, eski adıyla RFC 7807) ve Spring bunu
`ProblemDetail` sınıfıyla destekliyor. Standart alanlar:

| Alan | Ne yazar |
|---|---|
| `type` | Hata **türünü** tanımlayan adres — istemci buna göre dallanır |
| `title` | İnsan tarafından okunabilir kısa başlık |
| `status` | HTTP durum kodu |
| `detail` | Bu **tek olaya** özgü açıklama |
| `instance` | Hatanın oluştuğu adres |

Ayrıca istediğin kadar **kendi alanını** ekleyebilirsin.

⚠️ `type` ile `detail` arasındaki farkı kaçırma: `type` **bütün** "sipariş bulunamadı"
hatalarında aynıdır — istemci ona bakarak program yazar. `detail` her olayda değişir —
insan okur. İstemcinin `detail` metnine göre `if` yazması gerekiyorsa sözleşmeni yanlış
tasarlamışsındır.

## 2. En sade hâl: tek bir exception'ı ele al

```java
package tr.loncademy.siparis.web;

import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import java.net.URI;

@RestControllerAdvice                    // tüm kontrolcüler için geçerli
public class HataIsleyici {

    @ExceptionHandler(SiparisBulunamadi.class)
    public ProblemDetail bulunamadi(SiparisBulunamadi ex) {
        ProblemDetail p = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        p.setTitle("Sipariş bulunamadı");
        p.setType(URI.create("https://loncademy.tr/hatalar/siparis-bulunamadi"));
        return p;
    }
}
```

Gerçek çıktı:

```
HTTP/1.1 404
Content-Type: application/problem+json

{"detail":"Sipariş bulunamadı: yok",
 "instance":"/siparisler/yok",
 "status":404,
 "title":"Sipariş bulunamadı",
 "type":"https://loncademy.tr/hatalar/siparis-bulunamadi"}
```

İki şeye dikkat:

1. **`Content-Type: application/problem+json`** — `application/json` değil. İstemci
   başlığa bakarak "bu bir hata gövdesi" diyebilir.
2. **`instance` alanını sen yazmadın** — Spring isteğin yolunu kendisi koydu.

## 3. Doğrulama hatalarını anlamlı hâle getirmek ⭐

Asıl kazanç burada. `@Valid` başarısız olduğunda Spring
`MethodArgumentNotValidException` atar; onu yakalayıp alan alan açalım:

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ProblemDetail gecersiz(MethodArgumentNotValidException ex) {
    ProblemDetail p = ProblemDetail.forStatusAndDetail(
            HttpStatus.BAD_REQUEST, "İstek gövdesi geçersiz.");
    p.setTitle("Doğrulama hatası");

    Map<String, String> alanlar = new LinkedHashMap<>();
    ex.getBindingResult().getFieldErrors()
      .forEach(h -> alanlar.put(h.getField(), h.getDefaultMessage()));
    p.setProperty("alanlar", alanlar);          // ← kendi alanın

    return p;
}
```

Aynı geçersiz istek, şimdi — gerçek çıktı:

```json
{"detail":"İstek gövdesi geçersiz.",
 "instance":"/siparisler",
 "status":400,
 "title":"Doğrulama hatası",
 "alanlar":{"urunKodu":"must not be blank",
            "adet":"must be greater than or equal to 1"}}
```

Bunu bu bölümün başındaki yanıtla yan yana koy. Aynı istek, aynı hata — ama artık
mobil geliştirici formda **hangi kutunun** altına **ne** yazacağını biliyor.

⚠️ Kısıt mesajları varsayılan olarak İngilizce (`must not be blank`). Türkçeleştirmek
için kısıta mesaj ver:

```java
public record YeniSiparis(
        @NotBlank(message = "Ürün kodu boş olamaz") String urunKodu,
        @Min(value = 1, message = "Adet en az 1 olmalı") int adet) {}
```

## 4. Kolay yol: yerleşik hataları da standarda çevirmek

Kendi yazmadığın hatalar (405, 415, bozuk JSON) hâlâ eski biçimde dönüyor. Tek satırla
hepsini standarda çevirebilirsin:

```properties
spring.mvc.problemdetails.enabled=true
```

Varsayılanı **`false`**. Açtığında yerleşik hatalar da `problem+json` olur — gerçek çıktı:

```
$ curl -X DELETE localhost:8080/siparisler/1
{"detail":"Method 'DELETE' is not supported.","instance":"/siparisler/1",
 "status":405,"title":"Method Not Allowed"}
```

| | Ayar kapalı (varsayılan) | Ayar açık |
|---|---|---|
| Gövde | `{"timestamp","status","error","path"}` | RFC 9457 `problem+json` |
| `Content-Type` | `application/json` | `application/problem+json` |
| Alan ayrıntısı | Yok | Yok — onu **sen** eklersin (3. bölüm) |

📌 Bu ayar **biçimi** düzeltir, **içeriği** değil. Alan bazlı ayrıntı için yine kendi
işleyicini yazman gerekir. İkisini birlikte kullan.

## 5. Exception tasarımı ⭐

İşleyici yazmak yetmez; **hangi exception'ı atacağın** da bir tasarım kararı.

```java
public class SiparisBulunamadi extends RuntimeException {
    public SiparisBulunamadi(String no) { super("Sipariş bulunamadı: " + no); }
}
```

| Kural | Neden |
|---|---|
| **Unchecked exception** (`RuntimeException`) kullan | Checked exception her katmana `throws` yazdırır; ayrıca `@Transactional` checked exception'larda geri alma **yapmaz** (**201**) |
| **Alan adı taşı, HTTP kodu taşıma** | `SiparisBulunamadi` iyi; `NotFoundException` web katmanına bağımlılık yaratır |
| Exception'ı **servis katmanı** atsın | Kontrolcü ince kalsın |
| HTTP kodu eşlemesi **tek yerde** olsun | `@RestControllerAdvice` |

📌 Terimler: **checked exception** derleyicinin `throws` ya da `catch` yazmaya zorladığı
exception'lar; **unchecked exception** `RuntimeException` ailesinden gelen, böyle bir
zorunluluğu olmayanlar.

### ⚠️ Yutulmuş exception

```java
try {
    odemeAl(siparis);
} catch (Exception e) {
    return null;                     // ← hata kayboldu
}
```

İstemci `200 OK` ve boş gövde alır. Sunucu günlüğünde iz yok. **Bu, exception handling'in
tersidir.** Yakalayacaksan ya anlamlı bir exception'a çevir ya da günlüğe yaz ve yeniden at.

## 6. Ne kadarını söylemeli ⭐

```java
@ExceptionHandler(Exception.class)
public ProblemDetail beklenmeyen(Exception ex) {
    log.error("Beklenmeyen hata", ex);                    // ← ayrıntı GÜNLÜĞE
    ProblemDetail p = ProblemDetail.forStatusAndDetail(
            HttpStatus.INTERNAL_SERVER_ERROR,
            "Beklenmeyen bir hata oluştu.");              // ← istemciye GENEL mesaj
    p.setProperty("izlemeNo", MDC.get("traceId"));        // ← ikisini bağlayan numara
    return p;
}
```

Kural: **ayrıntı günlüğe, genel mesaj istemciye, ikisini bağlayan bir izleme numarası
yanıta.** Kullanıcı sana "izleme numaram `abc-123`" der, sen günlükte tam stack trace'i
bulursun.

⚠️ **Stack trace'i (hata anındaki çağrı zincirinin dökümü) istemciye asla gönderme.**
Sınıf adların, kütüphane sürümlerin ve dosya yolların saldırgana harita çizer. `server.error.include-stacktrace`
varsayılanı `never`; **değiştirme.**

## 7. Yanlış hâlleri

### ❌ Hata 1 — her kontrolcüde `try/catch`

```java
@GetMapping("/{no}")
public ResponseEntity<?> getir(@PathVariable String no) {
    try {
        return ResponseEntity.ok(servis.getir(no));
    } catch (SiparisBulunamadi e) {
        return ResponseEntity.status(404).body(Map.of("hata", e.getMessage()));
    } catch (Exception e) {
        return ResponseEntity.status(500).body(Map.of("hata", "bir şeyler ters gitti"));
    }
}
```

20 uç noktada 20 kere tekrarlanır ve hepsi biraz farklı biçimde döner.
✅ **Doğrusu:** `@RestControllerAdvice` — eşleme tek yerde.

### ❌ Hata 2 — `@ControllerAdvice` yazmak

```java
@ControllerAdvice                      // ← @ResponseBody yok
public class HataIsleyici { ... }
```

[2.1](../02-anotasyon-haritasi/2.1-stereotype.md)'deki `@Controller` tuzağının aynısı:
dönen nesne view name (gösterilecek sayfanın adı) sanılır.
✅ **Doğrusu:** `@RestControllerAdvice`.

### ❌ Hata 3 — `detail` metnine göre istemci kodu yazdırmak

```json
{"detail":"Sipariş bulunamadı: S-100"}
```

İstemci `if (detail.startsWith("Sipariş bulunamadı"))` yazarsa, sen mesajı düzelttiğin gün
onun kodu kırılır.
✅ **Doğrusu:** `type` alanını ver, istemci ona baksın.

## Sık karıştırılanlar — tek tabloda

| Karışan | Doğrusu | Neden diğeri değil |
|---|---|---|
| `type` / `detail` | `type` **sabit** (makine okur), `detail` **olaya özgü** (insan okur) | `detail`'e göre kod yazan istemci, metni değiştirdiğinde kırılır |
| `application/json` / `application/problem+json` | Hata gövdesi **problem+json** | İstemci başlığa bakıp hata olduğunu anlar |
| `problemdetails.enabled` her şeyi çözer | **Biçimi** çözer, **içeriği** değil | Alan bazlı ayrıntıyı yine sen eklersin |
| `@ControllerAdvice` / `@RestControllerAdvice` | İkincisi | Birincisinde dönen nesne view name sanılır |
| Checked exception daha güvenli | **Unchecked kullan** | Her katmana `throws` yazdırır; `@Transactional` geri alma yapmaz (201) |
| Ayrıntılı hata istemciye yardım eder | **Stack trace sızıntıdır** | Ayrıntı günlüğe, izleme numarası yanıta |

## Nasıl karşına çıkar — örnek kalıplar

**Kalıp 1 — "İstemci hangi alanın hatalı olduğunu soruyor"**
> `MethodArgumentNotValidException` işleyicisi yok.

**Kalıp 2 — "Hata gövdeleri uç noktadan uç noktaya farklı"**
> Her kontrolcüde `try/catch` var. `@RestControllerAdvice`'a taşı.

**Kalıp 3 — "Hata yanıtında view çözme hatası alıyorum"**
> `@ControllerAdvice` yazılmış, `@RestControllerAdvice` olmalı.

**Kalıp 4 — "Yanıtta sınıf adlarımız görünüyor"**
> Stack trace sızıyor. `server.error.include-stacktrace=never`.

**Kalıp 5 — "Mesajı düzelttik, istemci uygulaması kırıldı"**
> İstemci `detail` metnine göre dallanıyor. `type` alanını ver.

## 60 saniyelik özet

- Hata yanıtı bir **sözleşmedir**; standardı **RFC 9457** ve Spring'deki karşılığı `ProblemDetail`.
- Alanlar: `type` (sabit, makine okur) · `title` · `status` · `detail` (olaya özgü, insan okur) · `instance`.
- `Content-Type` **`application/problem+json`** olur.
- Doğrulama ayrıntısı için `MethodArgumentNotValidException`'ı yakala, alan → mesaj haritasını
  `setProperty` ile ekle.
- `spring.mvc.problemdetails.enabled=true` (varsayılan **`false`**) yerleşik hataları da standarda çevirir —
  ama **biçimi** düzeltir, **içeriği** değil.
- Exception'lar **unchecked** olsun ve **alan adı** taşısın, HTTP kodu taşımasın.
- Eşleme tek yerde: **`@RestControllerAdvice`** (`@ControllerAdvice` değil).
- **Ayrıntı günlüğe, genel mesaj istemciye, izleme numarası ikisini bağlar.**
- **Stack trace'i asla döndürme**; `server.error.include-stacktrace` varsayılanı `never`, değiştirme.
- Exception'ı yutma: ya anlamlıya çevir, ya günlüğe yazıp yeniden at.
