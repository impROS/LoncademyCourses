# 2.2 — @Configuration ve gizli proxy

> **Alan:** Anotasyon haritası — ⭐ "Spring nasıl çalışıyor?" sorusunun en somut cevabı
> **Süre:** ~25 dakika okuma + 20 dakika pratik
> **Test:** [`2.2-test.html`](2.2-test.html) · 14 soru

---

## Neden bu konu

Şu kodu oku ve cevabı tahmin et:

```java
@Configuration
public class Yapilandirma {

    @Bean
    public Kaynak kaynak() { return new Kaynak(); }

    @Bean
    public String tuketici() {
        return kaynak().no + "," + kaynak().no;      // ← aynı metodu iki kere çağırdım
    }
}
```

`kaynak()` metodunu iki kere çağırdık. Sıradan Java'da `new Kaynak()` iki kere çalışır ve
**iki farklı nesne** çıkar. Yani cevabın `1,2` olması gerekir.

Ama çıktı `1,1` — **aynı nesne.**

Bu, Spring'te "sıradan Java gibi görünüp sıradan Java gibi davranmayan" ender yerlerden
biri. Nasıl olduğunu anlamak, sonraki iki kursta karşına çıkacak **proxy** (senin sınıfının
yerine geçip çağrıları araya giren nesne) kavramının en temiz örneğidir.

**Büyük fikir:** `@Configuration` sınıfını Spring olduğu gibi kullanmaz — çalışma
zamanında ondan bir **alt sınıf** üretir ve `@Bean` metotlarını ele geçirir.

---

## 1. Ölçüm: üç mod, üç farklı sonuç ⭐

Aynı kodu üç farklı biçimde işaretleyip çalıştırdım. Gerçek çıktı:

```
### full:1,1
### proxysiz:6,7
### lite:3,4
### tuketici1 sınıfı: tr.loncademy.siparis.ProxyDenemesi$FullMode$$SpringCGLIB$$0
### tuketici2 sınıfı: tr.loncademy.siparis.ProxyDenemesi$ProxysizMode
```

| Mod | Nasıl işaretlendi | Sonuç | Ne demek |
|---|---|---|---|
| **Full mode** | `@Configuration` | `1,1` | İki çağrı, **tek nesne** |
| **Proxysiz mod** | `@Configuration(proxyBeanMethods = false)` | `6,7` | İki çağrı, **iki nesne** |
| **Lite mode** | `@Component` + `@Bean` | `3,4` | İki çağrı, **iki nesne** |

> 📌 **Sayıların kendisi önemli değil.** Bunlar `Kaynak` nesnelerine kurulma sırasına göre
> verilen numaralar; senin makinende `2,2` ya da `4,5` çıkabilir. Bakman gereken tek şey:
> **iki sayı aynı mı, farklı mı.** Aynıysa proxy devrede, farklıysa değil.

Son iki satır asıl kanıt. Full mode'daki sınıfın adına bak:

```
ProxyDenemesi$FullMode$$SpringCGLIB$$0
                      ^^^^^^^^^^^^^^^
```

Bu senin yazdığın sınıf **değil.** Spring, `FullMode` sınıfının bir alt sınıfını çalışma
zamanında üretti. Proxysiz mod'da ise sınıf adı olduğu gibi — proxy yok.

---

## 2. Proxy ne yapıyor

Üretilen alt sınıf, her `@Bean` metodunu ezer (override) ve gövdesini şuna benzer bir
şeyle değiştirir:

```java
// Spring'in ürettiği alt sınıf — kavramsal karşılığı
@Override
public Kaynak kaynak() {
    if (containerDaVar("kaynak")) {
        return containerDanAl("kaynak");   // ← ikinci çağrıda buraya düşer
    }
    Kaynak k = super.kaynak();             // ← senin gövden yalnızca ilk seferde çalışır
    containerAKoy("kaynak", k);
    return k;
}
```

Yani `kaynak()` yazdığında aslında "container'dan (nesneleri kuran ve birbirine bağlayan
yapı) `kaynak` bean'ini ver" demiş oluyorsun. Metodun gövdesi bir kere çalışır.

**Sonuç:** `@Configuration` içinde `@Bean` metotlarını **birbirinden çağırabilirsin** ve
singleton'lık bozulmaz:

```java
@Configuration
public class IstemciYapilandirmasi {

    @Bean
    public HttpAyarlari ayarlar() {
        return new HttpAyarlari(Duration.ofSeconds(3));
    }

    @Bean
    public RestClient stokIstemcisi() {
        return kur(ayarlar(), "https://stok.sirket.com");    // ✅ singleton ayar nesnesi
    }

    @Bean
    public RestClient odemeIstemcisi() {
        return kur(ayarlar(), "https://odeme.sirket.com");   // ✅ AYNI ayar nesnesi
    }
}
```

Proxy olmasaydı iki farklı `HttpAyarlari` nesnesi kurulurdu.

---

## 3. Üç modin karşılaştırması ⭐

| | **Full mode** | **Proxysiz mod** | **Lite mode** |
|---|---|---|---|
| Yazımı | `@Configuration` | `@Configuration(proxyBeanMethods = false)` | `@Component` + `@Bean` |
| Proxy var mı | ✅ CGLIB alt sınıfı | ❌ | ❌ |
| `@Bean` metodunu çağırmak | Container'dan alır | **Yeni nesne** kurar | **Yeni nesne** kurar |
| Açılış maliyeti | Alt sınıf üretimi (küçük ama var) | Yok | Yok |
| Sınıf kısıtı | `final` **olamaz**, parametresiz constructor gerekir | Yok | Yok |
| Ne zaman kullan | **Varsayılan tercihin** | Metotlar birbirini çağırmıyorsa | ⚠️ Kullanma |

### Hangi modu seçmeli

**Varsayılan olarak `@Configuration` yaz.** Doğru olan davranışı verir ve sürprizi yoktur.

`proxyBeanMethods = false` yalnızca şu ikisi birden doğruysa:
1. O sınıftaki `@Bean` metotları **birbirini çağırmıyor**, ve
2. Açılış süresi ölçülebilir biçimde önemli (çok sayıda configuration sınıfı olan büyük uygulama).

⚠️ Spring Boot'un **kendi** auto-configuration (Spring'in senin yerine verdiği koşullu bean
kararları) sınıflarının çoğu `proxyBeanMethods = false` kullanır — çünkü yüzlerce tanesi
var ve hiçbiri birbirinin `@Bean` metodunu çağırmıyor. Kaynak koda bakıp "demek ki doğrusu
bu" diye kopyalama; onların şartları seninkinden farklı.

---

## 4. Lite mode: sessiz tuzak ⭐

En tehlikelisi üçüncüsü, çünkü **hata vermez**:

```java
@Service                              // ← @Configuration değil
public class SiparisServisi {

    @Bean
    public ObjectMapper ozelMapper() { return new ObjectMapper(); }
}
```

Bu kod derlenir, uygulama açılır, bean bile üretilir. Ama:
- `ozelMapper()` metodunu sınıf içinden çağıran her yer **yeni bir nesne** alır,
- ve bunu sana kimse söylemez.

`ObjectMapper` gibi kurulumu pahalı bir nesnede bu, sessiz bir bellek ve başarım sorunudur.

> 📌 **Sık yapılan hata:** `@Bean` metodunu bir `@Service` ya da `@Component` sınıfına
> koymak. Kural: **`@Bean` metotları `@Configuration` sınıflarında durur.** İstisnası yok.

---

## 5. Yanlış hâlleri

### ❌ Hata 1 — `final` `@Configuration` sınıfı

```java
@Configuration
public final class Yapilandirma { ... }        // ← alt sınıf üretilemez
```

```
BeanDefinitionParsingException: Configuration problem:
@Configuration class 'Yapilandirma' may not be final. Remove the final modifier to continue.
Offending resource: class path resource [tr/loncademy/siparis/Yapilandirma.class]
```

⚠️ Bu hatanın **`APPLICATION FAILED TO START` kutusu yoktur** — düz bir stack trace (hata
anındaki çağrı zincirinin dökümü) olarak gelir. [00.2](../00-baslangic/02-kurulum.md)'de
"önce kutuya bak" demiştik; kutu her zaman olmaz. Kutu yoksa stack trace'in **en üstteki**
`Caused by` satırını oku, en alttakini değil.

✅ **Doğrusu:** `final`'ı kaldır — ya da metotlar birbirini çağırmıyorsa
`@Configuration(proxyBeanMethods = false)` yaz; o zaman proxy üretilmediği için `final`
olabilir.

📌 Bu, Kotlin'de daha sık başa gelir: Kotlin'de sınıflar **varsayılan olarak** `final`'dır.

### ❌ Hata 2 — `@Bean` metodunu dışarıdan çağırmak

```java
@Service
public class SiparisServisi {
    private final IstemciYapilandirmasi yapilandirma;

    public void bir() {
        RestClient c = yapilandirma.stokIstemcisi();   // ← başka bean üzerinden çağrı
    }
}
```

Bu **çalışır** (proxy devrede olduğu için container'dan gelir) ama yanlış bir alışkanlıktır:
bean'i inject etmek yerine configuration sınıfını inject ediyorsun.

✅ **Doğrusu:** `RestClient`'i doğrudan inject et (`@Qualifier` ile).

### ❌ Hata 3 — proxy'ye güvenip `static` `@Bean` yazmak

```java
@Configuration
public class Yapilandirma {
    @Bean
    public static PropertySourcesPlaceholderConfigurer ayarCozucu() { ... }
}
```

`static` `@Bean` metotları proxy'den **geçmez** — ezilecek bir örnek metot yoktur.
Bu bilinçli bir kullanımdır (çok erken kurulması gereken bean'ler için) ama farkında ol:
`static` yazdığın anda singleton garantisini kaybedersin.

**Girme:** `static` `@Bean`'in ne zaman gerektiği — nadiren, ve gerektiğinde hata mesajı
sana söyler.

---

## Sık karıştırılanlar — tek tabloda

| Karışan | Doğrusu | Neden diğeri değil |
|---|---|---|
| `@Configuration` sıradan bir sınıf | **Değil** — çalışma zamanında alt sınıfı üretilir | Sınıf adında `$$SpringCGLIB$$` görürsün |
| `@Bean` metodunu çağırmak = `new` | Full mode'da **container'dan alır** | Hızlı ve lite mode'da gerçekten yeni nesne kurar |
| `proxyBeanMethods = false` daha iyidir | **Duruma bağlı** | Metotlar birbirini çağırıyorsa singleton'lığı bozar |
| `@Component` + `@Bean` çalışır | Çalışır ama **singleton yok** | Hata vermez — sessiz tuzağın tanımı |
| Spring'in kendi kodu böyle yapıyor | Onların şartları farklı | Yüzlerce configuration sınıfı var ve hiçbiri birbirini çağırmıyor |
| `static @Bean` de proxy'den geçer | **Geçmez** | Ezilecek örnek metot yoktur |

## 🖥 Pratik — proxy'yi yakala

> **Amaç:** Üç modin farkını kendi ölçümünle görmek · **Süre:** 20 dk
> **💸 Maliyet:** Yok

### Adımlar

1. `tr/loncademy/siparis/ProxyDenemesi.java` oluştur:

   ```java
   package tr.loncademy.siparis;

   import org.springframework.context.annotation.Bean;
   import org.springframework.context.annotation.Configuration;
   import org.springframework.stereotype.Component;

   public class ProxyDenemesi {

       public static class Kaynak {
           private static int sayac = 0;
           public final int no = ++sayac;        // her kurulan nesne yeni numara alır
       }

       @Configuration                                       // TAM KİP
       public static class FullMode {
           @Bean public Kaynak kaynakFull() { return new Kaynak(); }
           @Bean public String tuketici1() { return "tam:" + kaynakFull().no + "," + kaynakFull().no; }
       }

       @Configuration(proxyBeanMethods = false)             // HIZLI KİP
       public static class ProxysizMode {
           @Bean public Kaynak kaynakProxysiz() { return new Kaynak(); }
           @Bean public String tuketici2() { return "hizli:" + kaynakProxysiz().no + "," + kaynakProxysiz().no; }
       }

       @Component                                           // HAFİF KİP
       public static class LiteMode {
           @Bean public Kaynak kaynakLite() { return new Kaynak(); }
           @Bean public String tuketici3() { return "hafif:" + kaynakLite().no + "," + kaynakLite().no; }
       }
   }
   ```

2. `main` metoduna ekle:

   ```java
   System.out.println("### " + container.getBean("tuketici1"));
   System.out.println("### " + container.getBean("tuketici2"));
   System.out.println("### " + container.getBean("tuketici3"));
   System.out.println("### FullMode sınıfı:   " + container.getBean(ProxyDenemesi.FullMode.class).getClass().getName());
   System.out.println("### ProxysizMode sınıfı: " + container.getBean(ProxyDenemesi.ProxysizMode.class).getClass().getName());
   ```

3. Çalıştır.

- [ ] **Kontrol:** `tam:` satırında iki sayı **aynı**.
- [ ] **Kontrol:** `hizli:` ve `hafif:` satırlarında iki sayı **farklı**.
- [ ] **Kaydet:** `FullMode` sınıfının adında hangi ek var? ______

4. **Şimdi bilerek boz.** `FullMode` sınıfını `final` yap ve çalıştır.

- [ ] **Kontrol:** `@Configuration class 'FullMode' may not be final` hatasını aldın.
      Bu hata, proxy'nin gerçekten üretildiğinin ikinci kanıtı.
- [ ] **Kaydet:** Bu hata `APPLICATION FAILED TO START` kutusu içinde mi geldi? ______
      (Beklenen: hayır — düz stack trace. Her hata kutuya girmez.)

5. `final`'ı kaldır.

### Temizlik

`ProxyDenemesi.java` dosyasını silebilirsin. `main`'e eklediğin satırları da temizle.
`Ctrl+C`.

## Nasıl karşına çıkar — örnek kalıplar

**Kalıp 1 — `@Configuration class '...' may not be final`**
> Proxy üretilemiyor. `final`'ı kaldır ya da `proxyBeanMethods = false`.

**Kalıp 2 — "Aynı ayar nesnesinden iki tane kurulmuş"**
> `proxyBeanMethods = false` yazılmış ama metotlar birbirini çağırıyor.

**Kalıp 3 — "`ObjectMapper`'ım her yerde farklı davranıyor"**
> `@Bean` metodu `@Component` sınıfında (lite mode).

**Kalıp 4 — "Stack trace'te `$$SpringCGLIB$$` görüyorum"**
> Normal. Proxy sınıfın adı budur; hata değil.

**Kalıp 5 — Kotlin'de `@Configuration` açılmıyor**
> Kotlin sınıfları varsayılan olarak `final`. `open` yaz ya da `all-open` eklentisini kullan.

## 60 saniyelik özet

- `@Configuration` sınıfının **çalışma zamanında alt sınıfı üretilir** (CGLIB proxy'si).
- Proxy, `@Bean` metotlarını ezer: ikinci çağrıda gövde çalışmaz, **container'dan alınır**.
- Ölçülen sonuç: full mode `1,1` · proxysiz mod `6,7` · lite mode `3,4`.
- Kanıtı sınıf adında: `...$$SpringCGLIB$$0`.
- **Varsayılan tercihin `@Configuration`** olsun; `proxyBeanMethods = false` yalnızca
  metotlar birbirini çağırmıyorsa ve açılış süresi ölçülebilir biçimde önemliyse.
- **`@Bean` metotları `@Component` sınıfına yazılmaz** — hata vermez, singleton'lık sessizce kaybolur.
- Proxy'lenen `@Configuration` sınıfı **`final` olamaz** (Kotlin'de sık başa gelir).
- `static @Bean` metotları proxy'den geçmez.
