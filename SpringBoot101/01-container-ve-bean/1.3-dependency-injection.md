# 1.3 — Dependency injection ve belirsizlik

> **Alan:** Container ve bean'ler — ⭐ kursun en çok işine yarayacak konusu
> **Süre:** ~35 dakika okuma + 20 dakika pratik
> **Test:** [`1.3-test.html`](1.3-test.html) · 16 soru

---

## Neden bu konu

Spring Boot'ta karşılaşacağın hataların yarısı bu konudan çıkar. İyi haber: hepsi
aynı üç sorunun cevabıdır.

1. Container istediğin bean'i **bulamadı** mı?
2. Container **birden fazla** aday buldu, hangisini seçeceğini bilemedi mi?
3. Bean'ler **birbirini bekliyor** mu?

Bu konuyu bitirdiğinde bir hata mesajına bakıp hangi durumda olduğunu bir bakışta
söyleyeceksin.

**Büyük fikir:** Container bağımlılıkları **türe göre** arar. Tür tek bir adayla eşleşiyorsa
sorun yok. Sıfır aday varsa "bulamadım", birden çok aday varsa "seçemedim" der. Ad,
yalnızca tür yetmediğinde devreye giren **ikinci** ölçüttür.

---

## 1. Üç injection biçimi ve neden yalnızca biri doğru ⭐

Dependency injection (bir sınıfın ihtiyaç duyduğu parçaları kendisi kurmak yerine
dışarıdan alması) üç biçimde yazılır. Üçü de çalışır; yalnızca biri doğrudur.

### Constructor injection (doğru olan)

```java
@Service
public class SiparisServisi {
    private final StokIstemcisi stok;

    public SiparisServisi(StokIstemcisi stok) {      // ← @Autowired yazmana GEREK YOK
        this.stok = stok;
    }
}
```

⚠️ **Sınıfta tek constructor varsa `@Autowired` yazmazsın.** Spring 4.3'ten beri
gereksiz. İnternetteki eski örneklerde göreceksin; yazmasan da çalışır, yazsan da —
ama yazmamak günümüz alışkanlığı.

### Field injection (yazma)

```java
@Service
public class SiparisServisi {
    @Autowired
    private StokIstemcisi stok;          // ← kısa, ama üç derdi var
}
```

### Setter injection (nadiren)

```java
@Autowired
public void setStok(StokIstemcisi stok) { this.stok = stok; }
```

### Neden constructor ⭐

| Ölçüt | Constructor | Field injection |
|---|---|---|
| `final` yapabilir misin | ✅ Evet — nesne kurulduktan sonra değişemez | ❌ Hayır |
| Testte Spring'siz kurabilir misin | ✅ `new SiparisServisi(mockStok)` | ❌ Reflection ya da Spring gerekir |
| Eksik bağımlılık ne zaman anlaşılır | ✅ **Açılışta** — uygulama hiç kalkmaz | ⚠️ Kalkar, kullanınca `NullPointerException` |
| Çok fazla bağımlılık olduğunu görür müsün | ✅ Constructor 8 parametreye çıkınca göze batar | ❌ Alanlar alt alta gizlenir |
| Döngüsel bağımlılık | ✅ Açılışta yakalanır | ⚠️ Sessizce çalışabilir |

Üçüncü satır asıl sebep: **hata erken çıksın.** Dördüncü satır gizli bir hediye — yapıcı
metodun uzaması, sınıfın çok iş yaptığını sana **kod gözden geçirmeden** söyler.

> 📌 **Sık yapılan hata:** "Field injection daha kısa" diye onu seçmek. Kısa olan
> yazması; okuması ve test etmesi değil. Ekipte bu tartışma çıkarsa dayanağın üçüncü
> satırdır, estetik değil.

## 2. Container nasıl eşleştiriyor: önce tür, sonra ad ⭐

Container bir parametreyi doldururken şu sırayı izler:

```
1. Parametrenin TÜRÜNE uyan bean'leri bul
        ↓
   ┌─── 0 aday  → HATA: "required a bean of type ... could not be found"
   ├─── 1 aday  → onu kullan ✅
   └─── 2+ aday → 2. adıma geç
        ↓
2. Aralarında @Primary var mı?    → varsa onu kullan ✅
        ↓
3. @Qualifier verilmiş mi?        → verilen ada uyanı kullan ✅
        ↓
4. Parametrenin ADI bean adlarından biriyle aynı mı? → onu kullan ✅
        ↓
   Hiçbiri değilse → HATA: "required a single bean, but N were found"
```

Bu sırayı **ezberle**. Injection hatalarının tamamı bu akışın bir adımında düğümlenir.

## 3. Belirsizlik: birden çok aday ⭐

[1.2](1.2-bean-tanimlama.md)'de iki `RestClient` tanımladık. Şimdi birini inject edelim:

```java
@Service
public class StokServisi {
    private final RestClient istemci;

    public StokServisi(RestClient istemci) {     // ← hangisi? stok mu, ödeme mi?
        this.istemci = istemci;
    }
}
```

Çalıştırınca (gerçek çıktı):

```
***************************
APPLICATION FAILED TO START
***************************

Description:

Parameter 0 of constructor in tr.loncademy.siparis.StokServisi required a single bean,
but 2 were found:
	- stokIstemcisi: defined by method 'stokIstemcisi' in class path resource
	  [tr/loncademy/siparis/IstemciYapilandirmasi.class]
	- odemeIstemcisi: defined by method 'odemeIstemcisi' in class path resource
	  [tr/loncademy/siparis/IstemciYapilandirmasi.class]

Action:

Consider marking one of the beans as @Primary, updating the consumer to accept multiple
beans, or using @Qualifier to identify the bean that should be consumed
```

Spring hatayı söylemekle kalmıyor, **üç çözümü de yazıyor.** Sırayla bakalım.

### Çözüm A — `@Qualifier` (en açık olan)

```java
public StokServisi(@Qualifier("stokIstemcisi") RestClient istemci) {
    this.istemci = istemci;
}
```

Adı **tüketen taraf** seçer. Okuyan kişi hangi bean'in geldiğini kodda görür.

### Çözüm B — `@Primary` (varsayılan ilan et)

```java
@Bean
@Primary
public RestClient stokIstemcisi() { ... }
```

"Belirtilmediyse bunu kullan." **Container genelinde** geçerli — dikkatli kullan: bir yerde
kolaylık, on yerde sürpriz olabilir.

### Çözüm C — parametre adını bean adıyla eşitle (kırılgan)

```java
public StokServisi(RestClient stokIstemcisi) { ... }    // parametre adı = bean adı
```

⚠️ **Bu çalışır ama kırılgandır** ve sebebini bilmen gerekiyor. Java, parametre adlarını
derlenmiş `.class` dosyasına **varsayılan olarak yazmaz**. Bu bilginin kalması için
derleyicinin `-parameters` bayrağıyla çalışması gerekir. Spring Boot'un Maven yapılandırması
bunu senin için açar — ama başka bir derleme düzeninde açık olmayabilir. Az önceki gerçek
hata çıktısının sonundaki şu satırı hatırla:

```
This may be due to missing parameter name information

Ensure that your compiler is configured to use the '-parameters' flag.
```

Yani bir gün "kodu değiştirmedim ama injection bozuldu" dersen, ilk bakacağın yer bu.
**Ezberleme, tanı:** parametre adına güvenme, `@Qualifier` yaz.

### Hangisini seç

| Durum | Seçim |
|---|---|
| İki adaydan biri "normal", diğeri özel durum | `@Primary` (normal olana) |
| Her tüketici farklı olanı istiyor | `@Qualifier` |
| Adayların hepsi lazım | Liste injection'ı (aşağıda) |
| Hızlı çözüm arıyorum | Parametre adı — **yapma**, kırılgan |

## 4. Hepsini birden almak: liste ve harita injection'ı ⭐

Aynı arayüzün birden çok gerçeklemesi varsa, hepsini birden isteyebilirsin:

```java
public interface OdemeYontemi {
    boolean destekliyorMu(String tur);
    void ode(long kurus);
}

@Component class KrediKarti implements OdemeYontemi { ... }
@Component class Havale     implements OdemeYontemi { ... }
@Component class Kapida     implements OdemeYontemi { ... }
```

```java
@Service
public class OdemeServisi {
    private final List<OdemeYontemi> yontemler;      // ← üçü de gelir

    public OdemeServisi(List<OdemeYontemi> yontemler) {
        this.yontemler = yontemler;
    }

    public void ode(String tur, long kurus) {
        yontemler.stream()
                 .filter(y -> y.destekliyorMu(tur))
                 .findFirst()
                 .orElseThrow(() -> new IllegalArgumentException("bilinmeyen ödeme türü: " + tur))
                 .ode(kurus);
    }
}
```

Bu, bu kursun **en çok işine yarayacak kalıbı**. Dördüncü bir ödeme yöntemi eklemek için
`OdemeServisi`'ne dokunmazsın — yeni bir `@Component` sınıfı yazarsın, liste kendiliğinden
büyür. (**301**'de bunun bir tasarım deseni olduğunu göreceğiz.)

Harita da alabilirsin — anahtar **bean adı** olur:

```java
public OdemeServisi(Map<String, OdemeYontemi> yontemler) { ... }
// { "krediKarti": ..., "havale": ..., "kapida": ... }
```

Sıra önemliyse `@Order` kullan (küçük sayı önce gelir):

```java
@Component
@Order(1)
class KrediKarti implements OdemeYontemi { ... }
```

⚠️ **Boş liste tuzağı:** Hiç gerçekleme yoksa Spring **boş liste** inject eder, hata
vermez. `yontemler.isEmpty()` durumunu düşünmediysen sessiz bir arıza yaşarsın.

## 5. İsteğe bağlı bağımlılık

Bean varsa kullan, yoksa devam et:

```java
@Service
public class BildirimServisi {
    private final Optional<SmsIstemcisi> sms;

    public BildirimServisi(Optional<SmsIstemcisi> sms) { this.sms = sms; }

    public void bildir(String mesaj) {
        sms.ifPresent(s -> s.gonder(mesaj));
    }
}
```

`Optional<T>` ile sarmalarsan, bean yoksa açılış patlamaz.

> 📌 **Sık yapılan hata:** Her bağımlılığı `Optional` yapmak. `Optional` bir **tasarım
> kararıdır**: "bu parça gerçekten olmayabilir" demektir. Zorunlu bir bağımlılığı
> `Optional` yaparsan, eksik yapılandırmayı açılışta yakalama şansını kaybedersin.

## 6. Döngüsel bağımlılık ⭐

İki bean birbirini isterse:

```java
@Service
public class AServisi {
    public AServisi(BServisi b) { ... }
}

@Service
public class BServisi {
    public BServisi(AServisi a) { ... }      // ← döngü
}
```

Gerçek çıktı:

```
Description:

The dependencies of some of the beans in the application context form a cycle:

┌─────┐
|  AServisi defined in file [.../AServisi.class]
↑     ↓
|  BServisi defined in file [.../BServisi.class]
└─────┘

Action:

Relying upon circular references is discouraged and they are prohibited by default.
Update your application to remove the dependency cycle between beans. As a last resort,
it may be possible to break the cycle automatically by setting
spring.main.allow-circular-references to true.
```

Spring Boot 2.6'dan beri döngüler **varsayılan olarak yasak**. Hata mesajı sana bir kaçış
yolu gösteriyor (`spring.main.allow-circular-references=true`) ve aynı cümlede
"son çare" diyor.

⚠️ **O ayarı açma.** Döngü bir yapılandırma sorunu değil, **tasarım sorunudur**: A ile B
birbirinin işini yapıyor demektir. Üç gerçek çözüm:

| Çözüm | Ne zaman |
|---|---|
| **Ortak parçayı üçüncü bir sınıfa çıkar** | En sık doğru cevap. A ve B'nin paylaştığı iş `CServisi` olur, ikisi de ona bağlanır. |
| **Event kullan** | A, B'yi çağırmak yerine event yayınlar; B dinler. Bağı koparır. |
| **Sınırı yeniden çiz** | A ve B aslında tek bir sınıf olmalıydı, ya da sınır yanlış yerden geçmiş. |

> 📌 Field injection kullanırsan bu döngü **sessizce çalışabilir**, çünkü nesne önce
> yarım kurulur, sonra alanlar doldurulur. Yani field injection, tasarım hatanı senden
> saklar. Constructor injection'ın sana verdiği asıl hediye budur.

## Sık karıştırılanlar — tek tabloda

| Karışan | Doğrusu | Neden diğeri değil |
|---|---|---|
| Türe göre / ada göre eşleşme | Container **önce türe** bakar | Ad yalnızca tür yetmediğinde devreye girer |
| `@Qualifier` / `@Primary` | `@Qualifier` **tüketende**, `@Primary` **üretende** | `@Primary` container genelinde varsayılan ilan eder; `@Qualifier` tek bir noktada seçer |
| Tek constructor'da `@Autowired` | **Gerekmez** | Spring 4.3'ten beri otomatik; eski örneklerde görürsün |
| `required a bean ... could not be found` / `required a single bean, but 2 were found` | Birincisi **sıfır** aday, ikincisi **fazla** aday | Çözümleri taban tabana zıt: biri bean eklemek, diğeri seçmek |
| Boş liste | Hata **vermez** | `List<T>` injection'ında hiç aday yoksa boş liste gelir — kontrolü sen yaz |
| Döngüyü ayarla çözmek | Ayar döngüyü **gizler** | `allow-circular-references` tasarım sorununu çözmez, erteler |
| Parametre adına güvenmek | Kırılgan — `-parameters` bayrağına bağlı | Derleme ayarı değişirse injection kodu değişmeden bozulur |

## Nasıl karşına çıkar — örnek kalıplar

**Kalıp 1 — `required a bean of type '...' that could not be found`**
> Sıfır aday. Sınıf bean değil ya da taranmayan pakette (1.1).

**Kalıp 2 — `required a single bean, but 2 were found`**
> Fazla aday. `@Qualifier` ya da `@Primary`.

**Kalıp 3 — `The dependencies of some of the beans ... form a cycle`**
> Tasarım sorunu. Ortak parçayı üçüncü sınıfa çıkar.

**Kalıp 4 — "Yeni bir ödeme yöntemi ekleyince servisi de değiştirmem gerekiyor"**
> `List<T>` injection'ı kullanılmamış. Kalıbı uygula, `if/else` zincirini sil.

**Kalıp 5 — "Derleme ayarını değiştirdik, injection bozuldu"**
> Parametre adına güvenilmiş, `-parameters` kapanmış. `@Qualifier` yaz.

**Kalıp 6 — "Listeye eleman gelmiyor ama hata da yok"**
> Boş liste inject edilmiş; gerçeklemeler taranmayan pakette olabilir.

## 60 saniyelik özet

- **Constructor injection kullan.** `final` olur, Spring'siz test edilir, eksik bağımlılık açılışta patlar.
- Tek constructor'da **`@Autowired` yazma** — gereksiz.
- Eşleşme sırası: **tür → `@Primary` → `@Qualifier` → parametre adı.**
- **0 aday** = "could not be found"; **2+ aday** = "required a single bean, but N were found". Çözümleri zıttır.
- `@Qualifier` **tüketende**, `@Primary` **üretende**.
- Parametre adına güvenme — `-parameters` derleyici bayrağına bağlıdır, kırılgandır.
- `List<T>` injection'ı tüm gerçeklemeleri getirir; yeni gerçekleme eklemek mevcut kodu değiştirmez.
- Hiç aday yoksa `List<T>` **boş** gelir, hata vermez — bu durumu sen kontrol et.
- `Optional<T>` bir tasarım kararıdır, hata bastırma aracı değil.
- Döngüsel bağımlılık **yasaktır ve tasarım sorunudur**. `allow-circular-references` açma.
