# 1.5 — Scope ve scoped proxy

> **Alan:** Container ve bean'ler
> **Süre:** ~25 dakika okuma + 15 dakika pratik
> **Test:** [`1.5-test.html`](1.5-test.html) · 14 soru

---

## Neden bu konu

Bu konu, **üretimde en pahalı sessiz hatanın** kaynağı: bir kullanıcının verisini başka
bir kullanıcıya göstermek.

Sebebi tek cümle: **bir singleton bean'in — yani container'da tek bir nesnesi olan bean'in
— alanı, bütün kullanıcılar arasında paylaşılır.** Bunu bilmeyen biri "şuraya oturum
bilgisini koyayım" der ve kod geliştirmede kusursuz çalışır — çünkü geliştirmede tek
kullanıcı vardır. Üretimde yüz kullanıcı olunca birbirlerinin verisini görürler.

**Büyük fikir:** Scope (bir bean'in kaç nesneye karşılık geldiğini ve ne kadar
yaşayacağını belirleyen ayar), "bu bean definition'dan kaç nesne üretilecek ve ne kadar
yaşayacak" sorusunun cevabıdır. Varsayılan cevap: **bir tane, uygulama boyunca.**

---

## 1. Dert: singleton bean'e durum yazmak ⭐

```java
@Service
public class SiparisServisi {
    private String suAnkiKullanici;              // ← ❌ FELAKET

    public void siparisAl(String kullanici, Siparis s) {
        this.suAnkiKullanici = kullanici;
        // ... uzun işlemler ...
        depo.kaydet(s, this.suAnkiKullanici);
    }
}
```

Bu koddaki hata görünmez, çünkü tek kullanıcıyla test edersen hep doğru çalışır.

**Ne oluyor:** `SiparisServisi`'nden container'da **tek bir nesne** var. Ayşe ve Mehmet aynı anda
sipariş verdiğinde ikisi de **aynı nesnenin aynı alanına** yazıyor:

```
zaman  Ayşe'nin thread'i                Mehmet'in thread'i            suAnkiKullanici
────────────────────────────────────────────────────────────────────────────────────
 t1    suAnkiKullanici = "ayse"                                       "ayse"
 t2                                     suAnkiKullanici = "mehmet"    "mehmet"
 t3    depo.kaydet(s, "mehmet") ← ❌                                  "mehmet"
```

Ayşe'nin siparişi Mehmet'in adına kaydedildi. Hata mesajı yok, günlükte iz yok.

### En sade hâl: durumu parametrede taşı

```java
@Service
public class SiparisServisi {

    public void siparisAl(String kullanici, Siparis s) {   // ← alan yok, parametre var
        depo.kaydet(s, kullanici);
    }
}
```

**Kural:** Singleton bir bean'in alanları **değişmez (immutable)** olmalı — constructor'da
atanan `final` bağımlılıklar ve ayarlar. İstekten isteğe değişen hiçbir şey alanda durmaz.

> 📌 **Sık yapılan hata:** Bunu bir thread safety konusu sanıp `synchronized` eklemek.
> `synchronized` veriyi bozulmaktan korur ama **karışmaktan korumaz** — Ayşe yine
> Mehmet'in değerini okuyabilir, sadece sırayla okur. Çözüm kilit değil, **alanı hiç
> kullanmamaktır.**

## 2. Scope türleri

| Scope | Kaç nesne | Ömrü | Ne zaman |
|---|---|---|---|
| **`singleton`** *(varsayılan)* | Container başına **1** | Uygulama boyunca | Neredeyse her zaman |
| **`prototype`** | Her istendiğinde **yeni** | Kullanan bırakınca | Durumu olan yardımcı nesneler |
| `request` | Her HTTP isteğinde 1 | İstek bitene kadar | İstek bağlamı taşıyan veriler |
| `session` | Her oturumda 1 | Oturum bitene kadar | Nadiren — dağıtık sistemde sorun çıkarır |
| `application` | `ServletContext` başına 1 | Uygulama boyunca | Çok nadir |

Yazımı:

```java
@Service
@Scope("prototype")
public class RaporUreticisi { ... }
```

Ya da tür güvenli sabitle:

```java
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
```

**Ezberle:** `singleton` varsayılandır ve %95 doğru cevaptır.
**Tanı, yeter:** `prototype` ve `request`.
**Girme:** `session` ve `application` — dağıtık bir sistemde ikisi de sorun kaynağıdır;
gerektiğinde bakarsın.

## 3. `prototype`'ın iki sürprizi ⭐

### Sürpriz 1 — `@PreDestroy` çağrılmaz

```java
@Component
@Scope("prototype")
public class DosyaYazici {
    @PreDestroy
    public void kapat() { ... }        // ← HİÇ ÇAĞRILMAZ
}
```

Container, prototype bean'i kurar ve **unutur** — ona bir daha referans tutmaz. Dolayısıyla ne
zaman öldüğünü bilemez, temizlik metodunu da çağıramaz.

✅ **Doğrusu:** Prototype bir bean kaynak tutuyorsa temizliğini **kullanan taraf** yapar
(`try-with-resources` gibi).

### Sürpriz 2 — singleton içine konursa bir kere kurulur ⭐

```java
@Service                                     // singleton
public class RaporServisi {
    private final RaporUreticisi uretici;    // prototype

    public RaporServisi(RaporUreticisi uretici) {
        this.uretici = uretici;              // ← BİR KERE inject edilir
    }

    public void rapor() {
        uretici.uret();                      // hep AYNI nesne
    }
}
```

`RaporUreticisi` prototype olsa bile, `RaporServisi` singleton olduğu için **bir kere** kurulur
ve o anda aldığı prototype nesneyi ömrü boyunca tutar. Yani prototype olmasının hiçbir
faydası kalmaz.

**Buna "scope uyumsuzluğu" (scope mismatch) denir.** Dar scope'lu bir bean, geniş
scope'lu bir bean'in içine sıkıştığında, geniş olanın ömrünü devralır.

---

## 4. Çözüm: scoped proxy ⭐

Uyumsuzluğu çözmenin yolu, inject edilen şeyin gerçek nesne değil, **her çağrıda doğru
nesneyi bulan bir proxy** olması:

```java
@Component
@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RaporUreticisi { ... }
```

Artık `RaporServisi`'ne inject edilen şey ince bir proxy'dir. Her metot çağrısında
container'a gider, o an için doğru nesneyi ister, çağrıyı ona iletir.

Aynı sorun `request` scope'unda daha da sık çıkar:

```java
@Component
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class IstekBaglami {
    private String izlemeNumarasi;
    // getter/setter
}
```

Proxy olmasaydı, singleton bir servise `IstekBaglami` inject etmek şu hatayı verirdi:

```
Scope 'request' is not active for the current thread; consider defining a scoped proxy
for this bean if you intend to refer to it from a singleton
```

Hata mesajı çözümü doğrudan söylüyor: *"consider defining a scoped proxy"*.

| `proxyMode` | Ne yapar |
|---|---|
| `ScopedProxyMode.NO` *(varsayılan)* | Proxy yok — uyumsuzluk sorunu yaşarsın |
| `ScopedProxyMode.TARGET_CLASS` | Sınıfın alt sınıfı üretilir (CGLIB) — **çoğu durumda bunu kullan** |
| `ScopedProxyMode.INTERFACES` | Arayüz üzerinden proxy — sınıf bir arayüz gerçekliyorsa |

⚠️ `TARGET_CLASS` proxy'si, sınıfın alt sınıfını ürettiği için sınıf `final` **olamaz** ve
parametresiz bir constructor'a ihtiyaç duyabilir.

---

## 5. Alternatif: `ObjectProvider`

Proxy yerine, ihtiyaç anında container'dan taze nesne isteyebilirsin:

```java
@Service
public class RaporServisi {
    private final ObjectProvider<RaporUreticisi> saglayici;

    public RaporServisi(ObjectProvider<RaporUreticisi> saglayici) {
        this.saglayici = saglayici;
    }

    public void rapor() {
        RaporUreticisi uretici = saglayici.getObject();   // ← her çağrıda YENİ
        uretici.uret();
    }
}
```

| | Scoped proxy | `ObjectProvider` |
|---|---|---|
| Kod nerede değişir | **Üreten** tarafta (`@Scope`) | **Tüketen** tarafta |
| Görünürlük | Gizli — bakan kişi proxy olduğunu anlamaz | Açık — kodda `getObject()` görünür |
| Sınıf kısıtı | `final` olamaz | Yok |
| Ne zaman | Var olan kodu değiştirmeden çözmek | Yeni kod yazarken, açıklık istiyorsan |

`ObjectProvider` ayrıca isteğe bağlı bean'ler için de kullanılır:
`saglayici.getIfAvailable()`, `saglayici.ifAvailable(x -> ...)`.

## 6. Yanlış hâlleri

### ❌ Hata 1 — singleton bean'e istek verisi yazmak

Yukarıdaki 1. bölümdeki kod. Hata vermez, üretimde veri karışır.
✅ **Doğrusu:** Durumu parametrede taşı.

### ❌ Hata 2 — proxy'siz `request` scope'u

```java
@Component
@Scope("request")                       // ← proxyMode yok
public class IstekBaglami { ... }

@Service
public class SiparisServisi {
    public SiparisServisi(IstekBaglami baglam) { ... }    // singleton içine dar scope
}
```

```
Error creating bean with name 'siparisServisi': Scope 'request' is not active for the
current thread
```

✅ **Doğrusu:** `@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)`

### ❌ Hata 3 — prototype'tan temizlik beklemek

```java
@Component
@Scope("prototype")
public class GeciciDosya {
    @PreDestroy public void sil() { dosya.delete(); }   // ← çağrılmaz, dosya birikir
}
```

✅ **Doğrusu:** Temizliği kullanan taraf yapar.

## Sık karıştırılanlar — tek tabloda

| Karışan | Doğrusu | Neden diğeri değil |
|---|---|---|
| Varsayılan scope | **`singleton`** | Java'da `new` her seferinde yeni nesne verir; Spring'in varsayılanı tersidir |
| Singleton = thread-safe | **Hayır** | Singleton'lık nesne sayısıyla ilgili; güvenliği alanı olmamak sağlar |
| `synchronized` çözer | **Çözmez** | Veri bozulmasını engeller, kullanıcıların birbirini görmesini engellemez |
| Prototype = her kullanımda yeni | Yalnızca **her istendiğinde** yeni | Singleton içine bir kere inject edilirse hep aynı nesne kalır |
| `@PreDestroy` prototype'ta | **Çağrılmaz** | Container prototype nesneye referans tutmaz, öldüğünü bilemez |
| `TARGET_CLASS` / `INTERFACES` | `TARGET_CLASS` çoğu durumda | `INTERFACES` yalnızca arayüz üzerinden erişiliyorsa; sınıf `final` olamaz uyarısı `TARGET_CLASS` içindir |

## 🖥 Pratik — scope farkını ölç

> **Amaç:** Singleton ve prototype farkını nesne kimliğiyle görmek · **Süre:** 15 dk
> **💸 Maliyet:** Yok

### Adımlar

1. İki sınıf oluştur:

   ```java
   package tr.loncademy.siparis;

   import org.springframework.stereotype.Component;

   @Component
   public class SingletonOrnek {
       public SingletonOrnek() { System.out.println("SingletonOrnek kuruldu: " + hashCode()); }
   }
   ```

   ```java
   package tr.loncademy.siparis;

   import org.springframework.context.annotation.Scope;
   import org.springframework.stereotype.Component;

   @Component
   @Scope("prototype")
   public class PrototypeOrnek {
       public PrototypeOrnek() { System.out.println("PrototypeOrnek kuruldu: " + hashCode()); }
   }
   ```

2. `main` metoduna ekle:

   ```java
   System.out.println("--- singleton, 3 kere istendi ---");
   for (int i = 0; i < 3; i++) System.out.println(container.getBean(SingletonOrnek.class).hashCode());

   System.out.println("--- prototype, 3 kere istendi ---");
   for (int i = 0; i < 3; i++) System.out.println(container.getBean(PrototypeOrnek.class).hashCode());
   ```

3. Çalıştır.

- [ ] **Kontrol:** Singleton için üç satırda da **aynı** sayı çıktı.
- [ ] **Kontrol:** Prototype için üç **farklı** sayı çıktı.
- [ ] **Kaydet:** `PrototypeOrnek kuruldu:` satırı kaç kere yazıldı? ______

4. Şimdi scope uyumsuzluğunu gör. Bir singleton servise prototype inject et:

   ```java
   @Service
   public class UyumsuzlukOrnegi {
       private final PrototypeOrnek p;
       public UyumsuzlukOrnegi(PrototypeOrnek p) { this.p = p; }
       public int kimlik() { return p.hashCode(); }
   }
   ```

   `main`'de üç kere `container.getBean(UyumsuzlukOrnegi.class).kimlik()` yazdır.

- [ ] **Kontrol:** Üçü de **aynı** sayı — prototype olmasına rağmen tek nesne.
      İşte scope uyumsuzluğu budur.

5. `PrototypeOrnek`'e proxy ekle:

   ```java
   @Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
   ```

- [ ] **Kontrol:** Artık üç **farklı** sayı çıkıyor.

## Nasıl karşına çıkar — örnek kalıplar

**Kalıp 1 — "Kullanıcılar birbirinin verisini görüyor"**
> Singleton bir bean'in alanında istek verisi tutuluyor. Alanı sil, parametreye taşı.

**Kalıp 2 — `Scope 'request' is not active for the current thread`**
> Dar scope'lu bean, singleton içine proxy'siz inject edilmiş. `proxyMode = TARGET_CLASS`.

**Kalıp 3 — "Prototype yaptım ama hep aynı nesne geliyor"**
> Singleton bir bean'e bir kere inject edilmiş. Proxy ya da `ObjectProvider` kullan.

**Kalıp 4 — "Geçici dosyalar birikiyor"**
> Prototype bean'de `@PreDestroy` bekleniyor; çağrılmıyor.

**Kalıp 5 — "Testte geçiyor, yük altında bozuluyor"**
> Neredeyse her zaman singleton bean'de paylaşılan durum.

## 60 saniyelik özet

- Varsayılan scope **`singleton`**: container başına bir nesne, uygulama boyunca.
- **Singleton bean'in alanına istekten isteğe değişen hiçbir şey yazma.** Bu, en pahalı sessiz hatadır.
- `synchronized` bu sorunu **çözmez**; çözüm alanı hiç kullanmamaktır.
- `prototype`: her **istendiğinde** yeni — ama singleton içine bir kere inject edilirse tek nesne kalır.
- Prototype bean'lerde **`@PreDestroy` çağrılmaz**; temizliği kullanan taraf yapar.
- Dar scope'u geniş scope'a inject ederken **scoped proxy** gerekir:
  `@Scope(value="request", proxyMode = ScopedProxyMode.TARGET_CLASS)`.
- `TARGET_CLASS` proxy'si alt sınıf ürettiği için sınıf `final` olamaz.
- Alternatif: **`ObjectProvider<T>`** — tüketen tarafta, açık ve görünür.
