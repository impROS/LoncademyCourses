# 1.3 — KRaft: metadata quorum ve controller

> **Alan:** Broker & Depolama Internals — Kafka 4.x'in tek çalışma modu
> **Süre:** ~30 dakika okuma + 20 dakika pratik
> **Test:** [`1.3-test.html`](1.3-test.html) · 14 soru

---

## Neden bu konu

Kafka 4.0 ile ZooKeeper **tamamen kaldırıldı**. Elindeki tüm operasyon bilgisi — "controller kim",
"metadata nasıl yayılır", "kaç node dayanır", "sürüm yükseltmesi nasıl olur" — değişti.
Bu konuyu atlarsan 5.3'teki arıza senaryolarında ne olduğunu anlayamazsın: cluster'ın "beyni"
artık Kafka'nın kendi log'udur ve o log'un kuralları normal topic'lerden farklıdır.

> **Büyük fikir:** KRaft ([Kafka’nın kendi Raft metadata katmanı ↗](../00-baslangic/02-kavram-sozlugu.md#kraft)), Kafka'nın kendi tasarımını kendine uygulamasıdır: **cluster metadata'sı da
> replike edilmiş bir log'dur.** Fark, bu log'un Raft ile yönetilmesi ve **çoğunluk (quorum)**
> gerektirmesidir — ISR ([lidere senkron replikalar kümesi ↗](../00-baslangic/02-kavram-sozlugu.md#isr)) gibi esnek değil, matematiksel olarak katıdır.

---

## 1. ZooKeeper neden gitti

| Problem (ZooKeeper dünyası) | KRaft'ta durum |
|---|---|
| İki ayrı dağıtık sistem işletmek (Kafka + ZooKeeper), iki ayrı güvenlik/izleme modeli | Tek sistem, tek binary, tek konfigürasyon |
| Controller failover'da metadata'yı ZooKeeper'dan **baştan okumak** (büyük cluster'da dakikalar) | Yeni controller zaten log'u takip ediyordu — failover **saniyeler** |
| Metadata değişikliği broker'lara tek tek RPC ([uzak yordam çağrısı ↗](../00-baslangic/02-kavram-sozlugu.md#rpc)) ile yayılırdı | Broker'lar metadata log'unu **takip eder** (fetch), delta uygular |
| Partition sayısı, ZooKeeper'ın veri düğümü (znode) limitleriyle sınırlıydı | Sınır log'un kendisi — milyon mertebesi partition hedeflenir |
| ZooKeeper ve Kafka metadata'sı ıraksayabilirdi (split-brain kaynağı) | Tek gerçeklik kaynağı: `__cluster_metadata` |

> ⚠️ **Tuzak:** "KRaft ZooKeeper'ın yerine geçen bir servis" değildir. **Kafka'nın içindeki bir Raft
> uygulamasıdır**; ayrı process, ayrı port, ayrı bağımlılık yoktur.

## 2. ⭐ Mimari: voter, observer, active controller

```
    ┌──────────── controller quorum (Raft voters) ────────────┐
    │  node 1 (leader/active controller)   node 2    node 3   │
    │        ▲ yazar                          ▲ fetch  ▲      │
    └────────┼─────────────────────────────────────────┼──────┘
             │  __cluster_metadata-0  (tek partition!)
    ┌────────┴───────── observers (broker'lar) ────────────────┐
    │  broker A          broker B          broker C            │
    │  metadata log'unu fetch eder, delta uygular              │
    └──────────────────────────────────────────────────────────┘
```

| Rol | Kim | Ne yapar |
|---|---|---|
| **Voter (oy veren controller düğümü)** | `controller.quorum.voters`'daki node'lar | Raft oylamasına katılır, metadata yazımını onaylar |
| **Leader (active controller)** | Voter'lardan biri | Metadata **yazan** tek node; lider seçimi, ISR değişimi, topic oluşturma |
| **Observer (yalnızca okuyan, oy vermeyen düğüm)** | Broker'lar | Yalnızca **okur**: metadata log'unu fetch eder, kendi belleğinde durumu kurar |

**Metadata bir topic'tir:** `__cluster_metadata`, **tek partition**, replikaları voter'lar.
Diskte tıpkı diğer partition'lar gibi görünür:

```
/var/lib/kafka/data/__cluster_metadata-0/
├── 00000000000000000000.log
├── 00000000000000000000.index      (10 MiB önceden ayrılmış)
├── 00000000000000000000.timeindex
├── 00000000000000002306.snapshot   ← anlık görüntü: yeni node'un baştan okumasını engeller
└── leader-epoch-checkpoint
```

**Snapshot neden var?** Metadata log'u sonsuza kadar büyüyemez. Controller periyodik olarak
"şu andaki tüm durum" anlık görüntüsü alır; yeni katılan bir node önce snapshot'ı yükler,
sonra üstüne son kayıtları uygular.

## 3. ⭐ Quorum matematiği: ISR'den farklı, daha katı

| | **ISR (veri partition'ları)** | **Raft quorum (metadata)** |
|---|---|---|
| Onay kuralı | ISR'deki herkes (ISR daralabilir) | **Kesin çoğunluk** — (N/2)+1 |
| Uyarlanabilir mi | Evet, ISR küçülür ve yazma devam edebilir | Hayır, çoğunluk yoksa yazma durur |
| 3 node ile kayıp toleransı | replication.factor−min.insync.replicas'e bağlı | **1** node |
| 5 node ile kayıp toleransı | — | **2** node |

| Voter sayısı | Çoğunluk | Tolere edilen kayıp | Kime uygun |
|---|---|---|---|
| 1 | 1 | 0 | Sadece geliştirme |
| **3** | 2 | **1** | Çoğu üretim cluster'ı |
| **5** | 3 | **2** | Büyük / kritik cluster (yazma gecikmesi biraz artar) |
| Çift sayı (2, 4) | — | Tek sayıdan fazla değil | **Kullanma** — fayda yok, maliyet var |

> ⚠️ **Tuzak (lab'da yaşayacaksın):** Combined modda broker ve controller aynı süreçtedir.
> 3 node'lu bir lab cluster'ında **iki node'u durdurmak** yalnızca broker'ları değil
> **controller quorum'unu da** öldürür; topic oluşturma gibi metadata işlemleri tamamen durur:
> `Cancelled createTopics request ... node 1 being disconnected`.

> **Hafıza kancası:** ISR "kim yetişebiliyorsa o", Raft "matematiksel çoğunluk". İkincisi pazarlık kabul etmez.

## 4. Combined mod ve isolated mod

| | **Combined** (`process.roles=broker,controller`) | **Isolated** (ayrı controller node'ları) |
|---|---|---|
| Node sayısı | Az; lab ve küçük cluster | Daha fazla; 3 controller + N broker |
| Risk | Broker yükü controller'ı etkiler; broker kaybı = quorum kaybı | Controller izole, öngörülebilir |
| Ölçek | Küçük | Üretim önerisi |
| Bizim lab | ✅ Bu (3 node, combined) | — |

> ⚠️ **Tuzak:** Combined mod **üretim için önerilmez.** Broker'da bir GC duraklaması ya da disk
> doygunluğu, aynı süreçteki controller'ın quorum'dan düşmesine yol açar — arıza yayılır.

## 5. Feature flag'ler: `metadata.version` ve arkadaşları

KRaft'ta sürüm yükseltmesi iki adımdır: **önce binary**, sonra **feature seviyesi**.
Cluster'ın mevcut hâli `kafka-features.sh` ile görülür (gerçek lab çıktısı):

```
Feature: eligible.leader.replicas.version  SupportedMaxVersion: 1        FinalizedVersionLevel: 1
Feature: group.version                     SupportedMaxVersion: 1        FinalizedVersionLevel: 1
Feature: kraft.version                     SupportedMaxVersion: 1        FinalizedVersionLevel: 0
Feature: metadata.version                  SupportedMaxVersion: 4.3-IV0  FinalizedVersionLevel: 4.3-IV0
Feature: share.version                     SupportedMaxVersion: 1        FinalizedVersionLevel: 1
Feature: streams.version                   SupportedMaxVersion: 1        FinalizedVersionLevel: 1
Feature: transaction.version               SupportedMaxVersion: 2        FinalizedVersionLevel: 2
```

| Feature | Ne kontrol eder | Nerede işleyeceğiz |
|---|---|---|
| `metadata.version` | Metadata kayıt formatı; tüm yeni özelliklerin tabanı | Bu konu |
| `eligible.leader.replicas.version` | ELR (KIP-966 — [ELR — güvenli lider adayları ↗](../00-baslangic/02-kavram-sozlugu.md#kip-966)) | 1.2 |
| `group.version` | Yeni consumer grup protokolü kayıtları (KIP-848 — [broker tarafı yeni consumer grup protokolü ↗](../00-baslangic/02-kavram-sozlugu.md#kip-848)) | 3.2 |
| `share.version` | Share group / kuyruk desteği (KIP-932 — [Kafka için kuyruklar / share group ↗](../00-baslangic/02-kavram-sozlugu.md#kip-932)) | 3.4 |
| `streams.version` | Streams rebalance protokolü (KIP-1071 — [Streams rebalance protokolü ↗](../00-baslangic/02-kavram-sozlugu.md#kip-1071)) | 6.1 |
| `transaction.version` | Transaction protokolü — **2 = TV2 (KIP-890 — [transaction protokolü TV2 ↗](../00-baslangic/02-kavram-sozlugu.md#kip-890))** | 4.1 |
| `kraft.version` | **1** = dinamik voter kümesi (KIP-853 — [dinamik KRaft quorum üyeliği ↗](../00-baslangic/02-kavram-sozlugu.md#kip-853)); **0** = statik voter listesi | Bu konu |

**Statik vs dinamik quorum:** Lab cluster'ımızda `kraft.version=0`, yani voter listesi
`controller.quorum.voters` ile **sabit**tir; controller eklemek/çıkarmak tüm node'ların
yapılandırmasını değiştirip yeniden başlatmayı gerektirir. `kraft.version=1` (KIP-853) ile
voter'lar **çalışırken** eklenip çıkarılabilir (`kafka-metadata-quorum.sh add-controller / remove-controller`).

> ⚠️ **Doğrulanmalı:** Feature yükseltmeleri **geri alınamaz** olabilir ve sürüme özgüdür.
> Üretimde `kafka-features.sh upgrade` çalıştırmadan önce kendi sürümünün resmî upgrade notlarını oku.

## 6. Controller failover'ı okumak

İki komut yeter:

```bash
# Kim lider, quorum sağlıklı mı?
kafka-metadata-quorum.sh --bootstrap-controller kafka-1:9093 describe --status

# Her voter ne kadar geride?
kafka-metadata-quorum.sh --bootstrap-controller kafka-1:9093 describe --replication
```

Gerçek lab çıktısı — sağlıklı hâl:

```
NodeId  LogEndOffset  Lag   LastFetchTimestamp   Status
1       3057          0     1788046399781        Leader
2       3057          0     1788046399373        Follower
3       3057          0     1788046399372        Follower
```

Lider node öldürüldükten sonra:

```
LeaderId:  2          (eskiden 1)
LeaderEpoch: 10       (eskiden 9)

NodeId  LogEndOffset  Lag    Status
2       3129          0      Leader
1       -1            3130   Follower     ← ölü node: LEO -1, Lag artıyor
3       3129          0      Follower
```

| Belirti | Anlamı |
|---|---|
| `LogEndOffset: -1` | O voter'a ulaşılamıyor |
| `Lag` sürekli artıyor | Voter geride kalmış ya da ölü |
| `LeaderEpoch` sık sık artıyor | Quorum kararsız — ağ ya da disk sorunu |
| `CurrentObservers` boş | Combined modda normaldir (broker'lar zaten voter) |

> ⭐ **Önemli fark:** Ölen controller lideri geri geldiğinde liderlik **ona geri dönmez.**
> Raft'ta "preferred leader" kavramı yoktur — veri partition'larındaki
> `auto.leader.rebalance` davranışı burada geçerli değildir.

## Sık karıştırılanlar — tek tabloda

| Karışan | Doğrusu | Neden diğeri değil |
|---|---|---|
| KRaft ↔ ZooKeeper yerine geçen servis | KRaft **Kafka'nın içinde** bir Raft uygulamasıdır | Ayrı process/port/bağımlılık yok |
| ISR ↔ Raft quorum | ISR uyarlanabilir; Raft **kesin çoğunluk** ister | Metadata'da "ISR daraldı ama devam" yok |
| Active controller ↔ partition lideri | Controller metadata liderinin **rolüdür**; partition lideri veri içindir | Bir node ikisini birden yapabilir ama kavramlar ayrıdır |
| `--bootstrap-server` ↔ `--bootstrap-controller` | Broker API'leri için ilki, quorum komutları için ikincisi | Quorum komutlarını broker portuna atarsan bağlanamazsın |
| Combined ↔ isolated | Combined lab için, isolated üretim için | Combined'da broker sorunu quorum'u da düşürür |
| `metadata.version` ↔ binary sürümü | Binary yükseltmek özelliği açmaz; feature seviyesi ayrıca yükseltilir | 4.3 binary'si eski `metadata.version` ile çalışabilir |
| Snapshot ↔ retention | Metadata snapshot'ı durumun tam kopyasıdır | Silme politikası değil, hızlı katılım mekanizmasıdır |

## 🖥 Pratik — controller'ı öldür, failover'ı ölç

> **Amaç:** Quorum'u okumak, controller failover'ını gözlemlemek, metadata log'unu diskte görmek · **Süre:** 20 dk
> **💸 Maliyet:** Yok.

### Adımlar

1. Quorum durumunu al ve **LeaderId**'yi not et:
   ```bash
   docker exec kafka-1 /opt/kafka/bin/kafka-metadata-quorum.sh \
     --bootstrap-controller kafka-1:9093 describe --status
   ```
2. Replikasyon tablosunu al — üç voter da `Lag: 0` olmalı:
   ```bash
   docker exec kafka-1 /opt/kafka/bin/kafka-metadata-quorum.sh \
     --bootstrap-controller kafka-1:9093 describe --replication
   ```
3. **Lider olan node'u öldür** (yukarıda not ettiğin id; örnekte 1):
   ```bash
   docker stop kafka-1
   ```
4. Hemen **başka bir node üzerinden** quorum'a bak:
   ```bash
   docker exec kafka-2 /opt/kafka/bin/kafka-metadata-quorum.sh \
     --bootstrap-controller kafka-2:9093 describe --status
   ```
   `LeaderId` değişmiş ve `LeaderEpoch` **1 artmış** olmalı.
5. Replikasyon tablosunda ölü node'u gör: `LogEndOffset: -1`, `Lag` artıyor.
6. Node'u geri başlat, liderliğin **geri dönmediğini** doğrula:
   ```bash
   docker start kafka-1 && sleep 10
   docker exec kafka-2 /opt/kafka/bin/kafka-metadata-quorum.sh \
     --bootstrap-controller kafka-2:9093 describe --status | head -3
   ```
7. Metadata log'unu diskte gör:
   ```bash
   docker exec kafka-2 bash -c 'ls -la /var/lib/kafka/data/__cluster_metadata-0/ | head'
   ```
8. Feature seviyelerini oku:
   ```bash
   docker exec kafka-2 /opt/kafka/bin/kafka-features.sh --bootstrap-server kafka-2:19092 describe
   ```

- [ ] **Kontrol:** Failover sonrası yeni `LeaderId` var ve `LeaderEpoch` arttı; node geri gelince liderlik geri dönmedi.
- [ ] **Kaydet:** Failover kaç saniye sürdü? ______ · `metadata.version` seviyesi? ______ ·
      `transaction.version` seviyesi? ______

### 💸 Temizlik
9. Üç node'un da ayakta olduğundan emin ol — bu labda topic oluşturmadık, silinecek bir şey yok:
   ```bash
   docker ps --format '{{.Names}}' | sort
   ```
- [ ] **Kontrol:** `kafka-1`, `kafka-2`, `kafka-3` üçü de listede.

## Nasıl karşına çıkar — örnek kalıplar

**Kalıp 1 — Quorum boyutlandırma**
> *"5 controller'lı bir quorum kaç node kaybını tolere eder?"* → **2.** Çoğunluk 3'tür.
> 4 controller da yine 2 tolere eder — çift sayı fayda getirmez.

**Kalıp 2 — Metadata işlemleri duruyor**
> *"Topic oluşturamıyoruz ama mevcut topic'lerden okuyabiliyoruz."*
> → Controller quorum'u çoğunluğu kaybetmiş. Broker'lar önbellekteki metadata ile okuma/yazmaya
> bir süre devam edebilir; **metadata yazan** işlemler durur.

**Kalıp 3 — Sürüm yükseltme**
> *"4.3 binary'sine geçtik ama yeni özellikler görünmüyor."*
> → `metadata.version` hâlâ eski seviyede. `kafka-features.sh describe` ile bak, gerekiyorsa
> `upgrade` ile yükselt (geri alınamaz olabilir — önce resmî notları oku).

**Kalıp 4 — Failover sonrası liderlik**
> *"Controller'ı restart ettik ama liderlik geri gelmedi, sorun mu?"*
> → Hayır. Raft'ta preferred leader yoktur; liderliğin nerede olduğu önemli değildir.

**Kalıp 5 — Mimari sorusu**
> *"Broker'lar metadata değişikliklerini nasıl öğrenir?"*
> → Push ile değil: broker'lar `__cluster_metadata` log'unu **observer olarak fetch eder** ve
> delta uygular. Bu yüzden metadata yayılımı ölçeklenir.

## 60 saniyelik özet

- Kafka 4.x **KRaft-only**; ZooKeeper yok. Metadata `__cluster_metadata` adlı **tek partition'lık** log'da.
- **Voter** = quorum üyesi (`controller.quorum.voters`), **observer** = broker; broker'lar metadata'yı **fetch eder**.
- **Active controller** = Raft lideri; metadata yazan tek node.
- Quorum **kesin çoğunluk** ister: 3 voter → 1 kayıp, 5 voter → 2 kayıp. Çift sayı anlamsız.
- **Snapshot**, yeni katılan node'un tüm log'u baştan okumasını engeller.
- **Combined mod** lab için; üretimde controller'ları **izole et**.
- Sürüm yükseltme iki adımlıdır: binary → `kafka-features.sh upgrade` (feature seviyesi).
- Feature'lar: `metadata.version`, `eligible.leader.replicas.version`, `group.version`,
  `share.version`, `streams.version`, `transaction.version` (**2 = TV2 — [Transaction Version 2 — her tx’te epoch artışı ↗](../00-baslangic/02-kavram-sozlugu.md#tv2)**), `kraft.version` (**1 = dinamik voter**).
- Failover'da `LeaderEpoch` artar; ölü voter `LogEndOffset: -1` gösterir; **liderlik geri dönmez**.
- Quorum komutları `--bootstrap-controller` ister, `--bootstrap-server` değil.
