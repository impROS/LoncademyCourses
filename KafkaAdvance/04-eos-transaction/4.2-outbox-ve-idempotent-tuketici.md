# 4.2 — Outbox ve idempotent tüketici desenleri

> **Alan:** Transaction & EOS — bu alanın son konusu; Kafka'nın **sınırının dışı**
> **Süre:** ~30 dakika okuma + 20 dakika pratik
> **Test:** [`4.2-test.html`](4.2-test.html) · 13 soru

---

## Neden bu konu

4.1'de öğrendik: Kafka'nın EOS ([exactly-once semantics — Kafka içi atomiklik ↗](../00-baslangic/02-kavram-sozlugu.md#eos))'u **Kafka içinde** geçerlidir. Gerçek sistemlerin çoğu ise
Kafka'nın **sınırını geçer**: veritabanına yazar, API çağırır, e-posta gönderir.

O sınırın iki yönünde iki klasik problem ve iki klasik çözüm vardır:

| Yön | Problem | Desen |
|---|---|---|
| **Kafka → dış sistem** | Duplicate işleme | **Idempotent tüketici** |
| **Dış sistem → Kafka** | Çift yazma (dual write) | **Outbox** |

Bu iki deseni bilmeden "mikroservisler arası tutarlılık" konuşulamaz.

> **Büyük fikir:** Dağıtık sistemlerde "tam bir kez teslim" imkânsızdır; **"tam bir kez etki"**
> mümkündür. Fark, teslimatı değil **etkiyi** tekilleştirmektir.

---

## 1. ⭐ Çift yazma (dual write) problemi

```java
// ❌ BOZUK: iki ayrı sistem, tek atomik blok YOK
@Transactional
public void siparisOlustur(Siparis s) {
    siparisRepository.save(s);              // 1) DB'ye yaz
    kafkaTemplate.send("siparisler", s);    // 2) Kafka'ya yaz  ← burada çökersen?
}
```

| Çöküş anı | Sonuç |
|---|---|
| DB commit'ten sonra, Kafka send'den önce | DB'de var, Kafka'da **yok** → aşağı akış sistemleri sipariş görmez |
| Kafka send'den sonra, DB commit'ten önce | Kafka'da var, DB'de **yok** → hayalet sipariş |
| `@Transactional` rollback olur ama Kafka'ya gitmiştir | Kafka geri alınamaz |

> ⚠️ **Tuzak:** `@Transactional` bir **veritabanı** transaction'ıdır; Kafka onun içinde değildir.
> "Spring hallediyor" varsayımı bu problemin en yaygın sebebidir.

---

## 2. ⭐ Outbox deseni: tek bir atomik yazma

**Fikir:** Kafka'ya doğrudan yazma. Mesajı **aynı veritabanı transaction'ında** bir `outbox`
tablosuna yaz. Ayrı bir süreç (relay) o tabloyu okuyup Kafka'ya basar.

```sql
CREATE TABLE outbox (
  id            UUID PRIMARY KEY,
  aggregate_id  VARCHAR(64)  NOT NULL,   -- Kafka key'i olacak (sıra için)
  topic         VARCHAR(128) NOT NULL,
  payload       JSONB        NOT NULL,
  created_at    TIMESTAMP    NOT NULL DEFAULT now(),
  published_at  TIMESTAMP                -- poller yaklaşımında kullanılır
);
```

```java
// ✅ DOĞRU: tek transaction, tek veritabanı
@Transactional
public void siparisOlustur(Siparis s) {
    siparisRepository.save(s);
    outboxRepository.save(new OutboxEvent(
            UUID.randomUUID(), s.getMusteriId(), "siparisler", toJson(s)));
}   // ikisi ya birlikte commit olur ya birlikte rollback
```

**Relay iki şekilde yapılır:**

| | **CDC (Debezium vb.)** | **Poller (zamanlanmış sorgu)** |
|---|---|---|
| Nasıl | DB'nin **write-ahead log**'unu okur | `SELECT ... WHERE published_at IS NULL` |
| Gecikme | Milisaniye | Poll aralığı kadar |
| DB yükü | Neredeyse yok | Sorgu + güncelleme yükü |
| Sıra | WAL sırası korunur | Sorgu sırasına bağlı |
| Karmaşıklık | Yüksek (ek altyapı) | Düşük |
| Ne zaman | Yüksek hacim, düşük gecikme | Küçük/orta hacim, sade mimari |

> ⭐ **Outbox at-least-once verir**, exactly-once değil: relay mesajı Kafka'ya yazıp
> `published_at`'i işaretlemeden çökerse mesaj **tekrar** gönderilir. Bu yüzden
> outbox **her zaman** tüketici tarafında idempotency ile eşleşmelidir.

**Sıra:** `aggregate_id`'yi Kafka key'i yaparsan aynı toplulaştırmanın (aggregate) olayları aynı
partition'a gider ve sıralı kalır (2.1). Bu, outbox'ın sessiz ama kritik ayrıntısıdır.

**Temizlik:** Outbox tablosu sonsuza kadar büyümemeli — yayınlanmış satırlar periyodik silinmeli
(ya da tablo partition'lanmalı).

## 3. ⭐ Idempotent tüketici: üç yol

### Yol A — Doğal idempotency (en iyisi)
İşlem zaten tekrar edilebilir yapıdaysa hiçbir ek mekanizma gerekmez.

| Doğal idempotent | Değil |
|---|---|
| `UPDATE hesap SET bakiye = 500` (mutlak değer) | `UPDATE hesap SET bakiye = bakiye + 10` (artımlı) |
| `INSERT ... ON CONFLICT DO UPDATE` (upsert) | Düz `INSERT` |
| `PUT /kaynak/42` | `POST /kaynak` |
| `SET durum = 'ONAYLANDI'` | `durum++` |

> **Hafıza kancası:** **Mutlak yazma idempotenttir, artımlı yazma değildir.** Tasarımda
> mümkünse olayı "yeni durum" olarak taşı, "delta" olarak değil.

### Yol B — Tekilleştirme tablosu (dedup)
```sql
CREATE TABLE processed_messages (
  message_id  VARCHAR(64) PRIMARY KEY,     -- UNIQUE kısıtı işi yapar
  processed_at TIMESTAMP NOT NULL DEFAULT now()
);
```
İş verisi + `processed_messages` kaydı **aynı transaction'da** yazılır. Duplicate gelirse
`INSERT` benzersizlik ihlali verir, transaction rollback olur ve **iş tekrarlanmaz**.

**`message_id` nereden gelir?**

| Kaynak | Artı | Eksi |
|---|---|---|
| **İş anahtarı** (`siparis_id`) | En doğrusu; iş anlamı taşır | Her olayda olmayabilir |
| Producer'ın ürettiği UUID (header) | Genel, kolay | Producer'ın **aynı** id ile yeniden göndermesi şart |
| `topic-partition-offset` | Her zaman var | Yeniden yazılan (replay/mirror) mesajlarda **değişir** |

### Yol C — Offset'i hedef sistemde tutmak
Offset'i iş verisiyle **aynı transaction'da** sakla ve Kafka'ya commit etme (3.3):

```
BEGIN
  iş verisini yaz
  UPDATE kafka_offsets SET offset = ? WHERE topic = ? AND partition = ?
COMMIT
-- Açılışta: onPartitionsAssigned → tablodan offset oku → consumer.seek(...)
```

Bu, **efektif exactly-once**'a en yakın yaklaşımdır: tek karar noktası vardır.
Bedeli: `kafka-consumer-groups --describe` artık gerçeği göstermez.

## 4. ⭐ Lab kanıtı: 30 duplicate, iki farklı sonuç

100 benzersiz iş, 30'u **bilerek iki kez** gönderildi (toplam 130 kayıt). Her kayıtta
`message-id` header'ı var. **Gerçek çıktı:**

```
===== Yazılan kayıt: 130 (benzersiz iş: 100) =====
  Beklenen doğru toplam bakiye: 1000
===== SONUÇ =====
  NAİF       toplam bakiye = 1300   ✗ BOZUK
  IDEMPOTENT toplam bakiye = 1000   ✓  (işlenen benzersiz iş: 100)
  Idempotent store'un kaydettiği offset: 130
```

Naif tüketici **%30 fazla** para yazdı. Aynı veri, aynı sıra, tek fark: `message-id` ile
tekilleştirme ve offset'in iş verisiyle aynı atomik blokta güncellenmesi.

Kodda kritik satır ([`SinkStore.java`](../lab/src/main/java/tr/improsy/kafkalab/k42/SinkStore.java)):

```java
if (!processedIds.add(messageId)) {   // UNIQUE(message_id) kısıtının karşılığı
    offsets.put(tp, nextOffset);      // duplicate olsa bile OFFSET İLERLEMELİ
    return false;                     // iş tekrarlanmaz
}
```

> ⚠️ **Tuzak:** Duplicate tespit ettiğinde offset'i ilerletmeyi unutursan tüketici o kayda
> takılır ve **sonsuza kadar** aynı duplicate'i işlemeye çalışır.

## 5. Tekilleştirme tablosunu yönetmek

Dedup tablosu sonsuza kadar büyüyemez. Üç strateji:

| Strateji | Nasıl | Risk |
|---|---|---|
| **TTL ([kaydın yaşam süresi ↗](../00-baslangic/02-kavram-sozlugu.md#ttl)) ile temizlik** | `DELETE WHERE processed_at < now() - interval '7 days'` | TTL, olası duplicate penceresinden **kısa** olmamalı |
| Doğal anahtar kullanmak | Ayrı tablo yok; iş tablosunun kendi `UNIQUE` kısıtı | Her olayda uygulanamaz |
| Bloom filter / cache + DB | Hızlı ön eleme, kesin karar DB'de | Ek karmaşıklık |

> **TTL kuralı:** Duplicate'ler ne kadar geriden gelebilir? Retention süresi, retry politikası ve
> replay ihtimalini düşün. `delete.retention.ms` (1.4) mantığının aynısı burada da geçerli.

## Sık karıştırılanlar — tek tabloda

| Karışan | Doğrusu | Neden diğeri değil |
|---|---|---|
| Outbox ↔ exactly-once | Outbox **at-least-once**'tır | Relay çöküşü tekrar gönderir; tüketici idempotent olmalı |
| `@Transactional` ↔ Kafka | DB transaction'ı Kafka'yı **kapsamaz** | Çift yazma problemi tam da budur |
| Idempotent producer ↔ idempotent tüketici | İlki Kafka'ya yazmayı (2.2), ikincisi **dış etkiyi** korur | Farklı katmanlar |
| `topic-partition-offset` ↔ iş anahtarı | Replay/mirror'da offset **değişir** | Kalıcı tekillik için iş anahtarı tercih edilir |
| Artımlı ↔ mutlak yazma | Mutlak yazma doğal idempotenttir | `bakiye + 10` tekrarlanınca bozar |
| CDC ↔ poller | İkisi de outbox relay'i | CDC düşük gecikme + ek altyapı; poller sade |
| Dedup tablosu temizliği ↔ opsiyonel | **Zorunlu** — yoksa tablo şişer | TTL duplicate penceresinden kısa olmamalı |

## Nasıl karşına çıkar — örnek kalıplar

**Kalıp 1 — Çift yazma**
> *"Sipariş DB'de var ama Kafka'da yok, bazen tersi."*
> → Klasik dual write. **Outbox** deseni.

**Kalıp 2 — Yanlış güven**
> *"`@Transactional` kullanıyoruz, Kafka gönderimi de geri alınır."*
> → Hayır. DB transaction'ı Kafka'yı kapsamaz; gönderilen mesaj geri alınamaz.

**Kalıp 3 — Çifte tahsilat**
> *"Bazı müşterilerden iki kez tahsilat yapıldı."*
> → At-least-once + artımlı yazma. `message-id` tabanlı dedup ya da mutlak yazma.

**Kalıp 4 — Kilitlenen tüketici**
> *"Duplicate tespit ediyoruz ama tüketici ilerlemiyor."*
> → Duplicate dalında offset ilerletilmemiş.

**Kalıp 5 — Şişen tablo**
> *"`processed_messages` tablosu 400 milyon satır."*
> → TTL temizliği yok. Duplicate penceresine göre bir saklama süresi belirle.

**Kalıp 6 — Replay sonrası bozulma**
> *"Topic'i yeniden oynattık, dedup çalışmadı."*
> → Kimlik `topic-partition-offset` üzerinden üretiliyordu; replay'de offsetler değişti.
> **İş anahtarı** kullan.

## 60 saniyelik özet

- Kafka EOS **sınırın dışına** geçmez. Dışarıda hedef "tam bir kez teslim" değil **"tam bir kez etki"**.
- **Çift yazma (dual write)** problemi: DB + Kafka'ya ayrı ayrı yazmak atomik değildir.
  `@Transactional` Kafka'yı **kapsamaz**.
- **Outbox:** mesajı iş verisiyle aynı DB transaction'ında bir tabloya yaz; relay (CDC ya da poller)
  Kafka'ya taşır. `aggregate_id` → Kafka key'i (sıra için). Tablo **temizlenmeli**.
- **Outbox at-least-once'tır** — tüketici tarafında idempotency **şart**.
- İdempotent tüketici üç yol: **doğal idempotency** (mutlak/upsert) · **dedup tablosu**
  (`UNIQUE(message_id)`) · **offset'i hedef sistemde tutmak**.
- Kimlik kaynağı tercihi: **iş anahtarı** > producer UUID header > `topic-partition-offset`
  (replay'de kırılır).
- **Duplicate'te bile offset ilerletilmeli** — yoksa tüketici kilitlenir.
- Lab: 130 kayıt / 100 benzersiz iş → naif **1300** (bozuk), idempotent **1000** (doğru).
- Dedup tablosunun TTL'i, duplicate'lerin gelebileceği en uzun pencereden **kısa olmamalı**.
