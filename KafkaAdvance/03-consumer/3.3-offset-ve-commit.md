# 3.3 — Offset yönetimi ve commit stratejileri

> **Alan:** Consumer Internals — "veri kayboldu" ve "iki kez işlendi"nin tüketici tarafı
> **Süre:** ~30 dakika okuma + 20 dakika pratik
> **Test:** [`3.3-test.html`](3.3-test.html) · 14 soru

---

## Neden bu konu

Offset commit'i **tek satırlık bir karardır** ama uçtan uca teslimat semantiğini o satır belirler.
Aynı kod, commit'i iki satır yukarı taşıdığında **veri kaybeden** bir sisteme dönüşür.

Bu konuda kanıt üreteceğiz: aynı senaryoyu iki commit sırasıyla çalıştırıp
**kayıp** ve **duplicate** listelerini yan yana göreceğiz.

> **Büyük fikir:** Commit "bu kayıtları işledim" demek değildir; **"bir dahaki sefere buradan
> devam et"** demektir. Bu yüzden commit'in **ne zaman** yapıldığı, ne yaptığından daha önemlidir.

---

## 1. ⭐ Offset nerede tutulur

| | Detay |
|---|---|
| Topic | `__consumer_offsets` |
| Partition sayısı | `offsets.topic.num.partitions` — varsayılan **50** |
| Politika | `compact` (1.4) — key başına son değer korunur |
| Key | `(group.id, topic, partition)` |
| Value | commit edilen offset + metadata |
| Saklama | `offsets.retention.minutes` — varsayılan **10080 (7 gün)** |

> ⚠️ **Tuzak:** Bir grup **7 gün** hiç commit etmezse offset'leri silinir. Uzun bakımdan dönen
> tüketici `auto.offset.reset`'e düşer: `latest` ise **aradaki tüm veriyi atlar**, `earliest`
> ise **her şeyi baştan işler**. İkisi de sürpriz olur.

**Commit edilen offset "sonraki okunacak offset"tir.** 0–9 arası kayıtları işlediysen commit
edeceğin değer **10**'dur. Elle commit ederken:

```java
consumer.commitSync(Map.of(tp, new OffsetAndMetadata(record.offset() + 1)));
//                                                                    ^^^ +1 unutulursa
//                                                  son kayıt her yeniden başlatmada tekrar işlenir
```

## 2. ⭐ Otomatik commit: kolay ama kontrolsüz

```properties
enable.auto.commit=true          # varsayılan
auto.commit.interval.ms=5000     # varsayılan
```

Otomatik commit **`poll()` çağrısı içinde** yapılır: bir sonraki `poll()`'da, üzerinden
`auto.commit.interval.ms` geçmişse **bir önceki poll'un döndürdüğü kayıtların tamamı** commit edilir.

| Sonuç | Açıklama |
|---|---|
| Kayıtları işlemeden bir sonraki `poll()`'a girersen | **Kayıp riski** — işlenmemiş kayıtlar commit edilmiş olur |
| Çöküş anına göre | Son 0–5 saniyelik iş **yeniden** işlenir (duplicate) |
| Kontrol | Yok — hangi kaydın commit edildiğini sen belirlemezsin |

> ⭐ **Kural:** İşleme **`poll()` döngüsünün içinde ve senkron** ise otomatik commit
> at-least-once'a yakın davranır. İşi **başka bir thread'e/kuyruğa** atıyorsan otomatik commit
> **veri kaybettirir** — çünkü Kafka "işledim" sanır.

## 3. ⭐ Elle commit: `commitSync` vs `commitAsync`

| | `commitSync()` | `commitAsync()` |
|---|---|---|
| Bloklar mı | Evet, cevabı bekler | Hayır |
| Retry | **Otomatik** (başarana kadar, timeout'a kadar) | **Yok** — geç gelen bir cevap eskiyi ezmesin diye |
| Hız | Yavaş | Hızlı |
| Kullanım | Kapanış, rebalance öncesi, kritik noktalar | Normal döngü |

**Üretim kalıbı — ikisi birlikte:**

```java
try {
    while (running) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
        for (ConsumerRecord<String, String> r : records) {
            process(r);                       // ÖNCE İŞLE
        }
        consumer.commitAsync();               // SONRA commit et (hızlı yol)
    }
} catch (WakeupException e) {
    // kapatma sinyali — normal
} finally {
    try {
        consumer.commitSync();                // son bir kez, garantili
    } finally {
        consumer.close();                     // gruptan düzgün ayrıl → hızlı rebalance
    }
}
```

> ⚠️ **Tuzak:** `commitAsync()` **retry yapmaz**. Sadece onu kullanan bir döngüde, son commit
> başarısız olursa fark etmezsin ve yeniden başlatmada o batch tekrar işlenir. `finally`'deki
> `commitSync()` bu deliği kapatır.

## 4. ⭐ Kanıt: commit sırası semantiği belirler

30 kayıt, tüketici 10 kayıt çekiyor, 5'ini işleyip **çöküyor**, sonra aynı grupla yeniden başlıyor.
**Gerçek lab çıktısı:**

```
===== ÖNCE COMMIT (at-most-once) =====
  commit edildi (işlemeden önce), 10 kayıt için
  işlendi: [0, 1, 2, 3, 4]  → ÇÖKÜŞ
  2. oturumda işlenen: 20 kayıt, ilk=10 son=29
  → HİÇ İŞLENMEYEN (kayıp) : [5, 6, 7, 8, 9]        ⬅ VERİ KAYBI
  → İKİ KEZ İŞLENEN        : yok

===== SONRA COMMIT (at-least-once) =====
  işlendi: [0, 1, 2, 3, 4]  → ÇÖKÜŞ
  2. oturumda işlenen: 30 kayıt, ilk=0 son=29
  → HİÇ İŞLENMEYEN (kayıp) : yok
  → İKİ KEZ İŞLENEN        : [0, 1, 2, 3, 4]        ⬅ DUPLICATE
```

**5 kayıt kaybı** ile **5 kayıt tekrarı** arasındaki tek fark, `commitSync()` çağrısının
işleme döngüsünün **öncesinde mi sonrasında mı** olduğudur.

> **Hafıza kancası:** **Önce commit = kayıp. Sonra commit = tekrar.**
> Kafka'da "kayıpsız ve tekrarsız" seçeneği bu iki satırın arasında yoktur —
> onu ancak transaction (4.1) ya da idempotent yazma (4.2) verir.

## 5. Rebalance sırasında commit: `ConsumerRebalanceListener`

Partition elinden alınmadan önce commit etmezsen, o partition'ın son işlenen kayıtları
yeni sahibi tarafından **yeniden işlenir**.

```java
consumer.subscribe(List.of(topic), new ConsumerRebalanceListener() {
    @Override public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
        // Son şansın: partition gitmeden önce ilerlemeyi kaydet
        consumer.commitSync(currentOffsets);
    }
    @Override public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
        // Gerekirse dış kaynaktan offset yükle ve seek() yap
    }
    @Override public void onPartitionsLost(Collection<TopicPartition> partitions) {
        // Cooperative protokolde: partition zaten kaybedildi, commit ETME — sahibi başkası
        cleanupLocalState(partitions);
    }
});
```

| Metot | Ne zaman | Ne yapmalısın |
|---|---|---|
| `onPartitionsRevoked` | Partition **düzenli olarak** alınmadan önce | **Commit et**, yerel durumu temizle |
| `onPartitionsAssigned` | Yeni partition atandıktan sonra | Gerekirse `seek()`, yerel durumu kur |
| `onPartitionsLost` | Partition **zaten kaybedildi** (üye atıldı) | **Commit etme** — sadece temizlik |

> ⚠️ **Tuzak:** `onPartitionsLost` içinde commit denemek `CommitFailedException` üretir;
> o partition artık senin değil.

## 6. Offset'i Kafka dışında tutmak

Kafka→veritabanı akışlarında **efektif exactly-once**'ın klasik yolu: offset'i **iş verisiyle
aynı transaction'da** saklamak.

```java
// tek DB transaction'ı içinde:
//   1) işlenen kayıtları yaz
//   2) (topic, partition) → offset satırını güncelle
// commit
// Kafka'ya commit YOK. Başlangıçta:
//   onPartitionsAssigned → DB'den offset oku → consumer.seek(tp, offset)
```

Bu, 4.2'de detaylandıracağımız desenin temelidir. Avantajı: **tek bir atomik karar noktası**.
Bedeli: `auto.offset.reset` ve `kafka-consumer-groups` gibi araçlar artık gerçeği göstermez —
gerçek offset veritabanındadır.

## 7. Offset sıfırlama ve taşıma (operasyon)

```bash
# ÖNİZLEME (--dry-run varsayılandır, --execute demezsen bir şey değişmez)
kafka-consumer-groups.sh --bootstrap-server kafka-1:19092 \
  --group odeme-tuketici --reset-offsets --to-earliest --topic odemeler --dry-run

# UYGULA (grup DURMUŞ olmalı — aktif üyesi varsa reddedilir)
kafka-consumer-groups.sh --bootstrap-server kafka-1:19092 \
  --group odeme-tuketici --reset-offsets --to-datetime 2026-08-01T00:00:00.000 \
  --topic odemeler --execute
```

| Seçenek | Ne yapar |
|---|---|
| `--to-earliest` / `--to-latest` | Log başı / sonu |
| `--to-offset N` | Belirli offset |
| `--to-datetime` | Zaman damgasından (`.timeindex`, 1.1) |
| `--shift-by N` | Göreli kaydırma (negatif = geri) |
| `--by-duration PT1H` | Son 1 saat |

> ⚠️ **Tuzak:** Reset komutu **yalnızca grubun aktif üyesi yokken** çalışır. Üretimde
> "tüketiciyi durdur → reset → başlat" sırası zorunludur, ve `--execute` demeden hiçbir şey değişmez.

## Sık karıştırılanlar — tek tabloda

| Karışan | Doğrusu | Neden diğeri değil |
|---|---|---|
| Commit "işledim" ↔ "buradan devam et" | Commit **sonraki okunacak offset**tir | `record.offset() + 1` yazılır |
| Otomatik commit güvenli ↔ duruma bağlı | Yalnızca işleme **poll döngüsünde senkronsa** kabul edilebilir | İşi kuyruğa atarsan kayıp üretir |
| `commitSync` ↔ `commitAsync` | İlki retry yapar ve bloklar; ikincisi yapmaz | Sadece async kullanmak son commit'i riske atar |
| `onPartitionsRevoked` ↔ `onPartitionsLost` | İlkinde commit **et**, ikincisinde **etme** | Lost'ta partition zaten senin değil |
| `auto.offset.reset` ↔ offset sıfırlama | İlki **offset yokken** devreye girer | Var olan offset'i değiştirmek `--reset-offsets` işidir |
| Offset topic'i ↔ normal topic | `__consumer_offsets` **compacted**tır | Retention `offsets.retention.minutes` (7 gün) |
| At-least-once ↔ exactly-once | Sonra-commit at-least-once verir | Tekrarsızlık için transaction/idempotent yazma gerekir |

## Nasıl karşına çıkar — örnek kalıplar

**Kalıp 1 — Asenkron işleme kaybı**
> *"Kayıtları bir thread pool'a atıyoruz, otomatik commit açık. Ara sıra kayıt kayboluyor."*
> → Kafka işlendi sanıyor. Ya işleme senkron olmalı ya da commit **iş bittikten sonra** elle yapılmalı.

**Kalıp 2 — Uzun bakım sonrası sürpriz**
> *"10 gün kapalı kalan tüketici açıldı ve tüm veriyi baştan işledi."*
> → `offsets.retention.minutes` (7 gün) doldu, offset silindi, `auto.offset.reset=earliest` devreye girdi.

**Kalıp 3 — Son batch tekrarı**
> *"Her deploy'da son birkaç yüz kayıt tekrar işleniyor."*
> → Kapanışta `commitSync()` yok ya da `close()` çağrılmıyor. `finally` bloğunu ekle.

**Kalıp 4 — Off-by-one**
> *"Her yeniden başlatmada aynı kayıt bir kez daha işleniyor."*
> → Elle commit'te `offset + 1` yerine `offset` yazılmış.

**Kalıp 5 — Reset reddediliyor**
> *"`--reset-offsets --execute` çalışmıyor."* → Grubun aktif üyesi var. Önce tüketiciyi durdur.

**Kalıp 6 — Rebalance'ta tekrar**
> *"Her rebalance'ta bir miktar kayıt yeniden işleniyor."*
> → `onPartitionsRevoked` içinde commit yok.

## 60 saniyelik özet

- Offsetler `__consumer_offsets`'te: **50 partition**, **compacted**, key = `(group, topic, partition)`,
  saklama **7 gün** (`offsets.retention.minutes=10080`).
- Commit edilen değer **sonraki okunacak offset**tir → `record.offset() + 1`.
- Otomatik commit `poll()` içinde, **5 saniyede bir**; işleme asenkronsa **kayıp üretir**.
- `commitSync` bloklar ve **retry yapar**; `commitAsync` hızlıdır ve **retry yapmaz**.
  Üretim kalıbı: döngüde async, `finally`'de sync.
- **Kanıt:** önce commit → 5 kayıt **kayıp**; sonra commit → 5 kayıt **duplicate**.
- `onPartitionsRevoked` → **commit et**; `onPartitionsLost` → **commit etme**, sadece temizle.
- Kafka dışı offset saklama (DB transaction'ı içinde) efektif exactly-once verir (4.2).
- `--reset-offsets` yalnızca **aktif üye yokken** ve `--execute` ile çalışır.
