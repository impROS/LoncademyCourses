# 5.2 — Metrikler ve izleme

> **Alan:** Operasyon — arıza anında ne izleyeceğini önceden bilmek
> **Süre:** ~28 dakika okuma + 20 dakika pratik
> **Test:** [`5.2-test.html`](5.2-test.html) · 14 soru

---

## Neden bu konu

Kafka **binlerce** JMX ([JVM metrik arayüzü ↗](../00-baslangic/02-kavram-sozlugu.md#jmx)) metriği yayınlar. Hepsini panoya koymak, hiçbirini koymamakla neredeyse
aynı şeydir. İşe yarayan yaklaşım şudur: **10-15 metriği ezbere bil**, geri kalanını arıza anında ara.

Bu konu ayrıca en sık yapılan izleme hatasını düzeltiyor: **lag'i tek bir sayı sanmak**.

> **Büyük fikir:** İyi bir Kafka panosunda üç soru cevaplanır: *Veri kayboluyor mu?* (replikasyon),
> *Sistem yetişiyor mu?* (lag ve kuyruklar), *Cluster sağlıklı mı?* (controller, offline partition).

## 1. ⭐ Alarm kurulacak metrikler — kısa liste

Bunlar **sayfa uyandıracak** metriklerdir:

| Metrik | Sağlıklı | Anlamı |
|---|---|---|
| `kafka.controller:type=KafkaController,name=ActiveControllerCount` | Cluster genelinde **toplam 1** | 0 = controller yok, >1 = split-brain |
| `kafka.controller:type=KafkaController,name=OfflinePartitionsCount` | **0** | >0 = lider bulunamayan partition var (**veri erişilemez**) |
| `kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions` | **0** | >0 = ISR ([lidere senkron replikalar kümesi ↗](../00-baslangic/02-kavram-sozlugu.md#isr)) eksik (1.2) |
| `kafka.server:type=ReplicaManager,name=UnderMinIsrPartitionCount` | **0** | >0 = `acks=all` **yazamıyor** |
| `kafka.server:type=ReplicaManager,name=AtMinIsrPartitionCount` | 0 | Sınırda; bir kayıp daha yazmayı durdurur |
| Consumer **partition başına** lag | Eşiğinin altında | Aşağıda detay |
| Disk doluluk oranı | < %75 | Kafka disk dolunca durur |

> ⚠️ **`ActiveControllerCount` tuzağı:** Bu metrik **broker başına** okunur ve controller olmayan
> broker'larda **0** döner. Lab'da `kafka-1` için 0 gördük — normal. Alarm kuralı
> **cluster genelindeki toplamın 1 olmasıdır.**

## 2. ⭐ Lag'i doğru ölçmek: ortalama yalan söyler

En yaygın izleme hatası: "toplam lag" ya da "ortalama lag" izlemek.

```
Toplam lag: 50.000        →  "idare eder"
Gerçek:  p0: 12  p1: 8  p2: 49.960  p3: 15  p4: 5   →  p2 BOĞULMUŞ
```

| Ne izlemeli | Neden |
|---|---|
| **Partition başına maksimum lag** | Tek bir sıcak partition'ı yakalar |
| **Lag'in türevi (artıyor mu?)** | Sabit 10.000 lag, artan 500 lag'den iyidir |
| **Zaman cinsinden lag** | "50.000 kayıt" anlamsız; "12 dakika geride" anlamlıdır |
| Consumer başına lag | Hangi instance takılmış |

**Client tarafı metrikler** (uygulamandan):

| Metrik | Anlamı |
|---|---|
| `records-lag-max` | Bu consumer'ın en kötü partition'ındaki lag |
| `records-consumed-rate` | Tüketim hızı |
| `fetch-latency-avg` | Broker cevap süresi |
| `commit-latency-avg` | Offset commit süresi |
| `rebalance-rate-per-hour`, `rebalance-latency-avg` | **Rebalance fırtınası göstergesi** (3.2) |
| `last-poll-seconds-ago` | ⭐ `max.poll.interval.ms` ([iki poll arası izin verilen süre ↗](../00-baslangic/02-kavram-sozlugu.md#maxpollintervalms))'e yaklaşıyor mu |

> ⭐ **`last-poll-seconds-ago` en az bilinen ama en faydalı metriktir:** rebalance fırtınası
> **olmadan önce** uyarır.

## 3. Broker metrikleri: kapasite ve doygunluk

| Metrik | Sağlıklı | Ne söyler |
|---|---|---|
| `kafka.server:type=KafkaRequestHandlerPool,name=RequestHandlerAvgIdlePercent` | **> 0.3** | Disk/istek işleyici doygunluğu → `num.io.threads` |
| `kafka.network:type=SocketServer,name=NetworkProcessorAvgIdlePercent` | **> 0.3** | Ağ thread doygunluğu → `num.network.threads` |
| `kafka.network:type=RequestMetrics,name=TotalTimeMs,request=Produce` | Kararlı | Yazma gecikmesi; bileşenlerine ayrılabilir |
| `kafka.server:type=BrokerTopicMetrics,name=BytesInPerSec` / `BytesOutPerSec` | Kapasiteye göre | Trafik |
| `kafka.log:type=LogFlushStats,name=LogFlushRateAndTimeMs` | Düşük | Disk yavaşlığı |
| `kafka.server:type=ReplicaFetcherManager,name=MaxLag` | Düşük | Replikasyon gecikmesi |

**Gerçek lab çıktısı** (JmxTool ile, kafka-1):

```
kafka.server:...,name=UnderReplicatedPartitions:Value               0
kafka.server:...,name=UnderMinIsrPartitionCount:Value               0
kafka.controller:...,name=ActiveControllerCount:Value               0   ← bu broker controller DEĞİL
kafka.controller:...,name=OfflinePartitionsCount:Value              0
kafka.server:...,name=BytesInPerSec  OneMinuteRate=33867.27  MeanRate=49561.73
kafka.server:...,name=RequestHandlerAvgIdlePercent  OneMinuteRate=1.000   ← boşta, doygun değil
kafka.network:...,name=NetworkProcessorAvgIdlePercent:Value         1.0
```

`TotalTimeMs` şu bileşenlere ayrılır — **hangi aşamada beklendiğini** söyler:

| Bileşen | Yüksekse |
|---|---|
| `RequestQueueTimeMs` | İstek kuyruğu dolu → `num.io.threads` |
| `LocalTimeMs` | Diske yazma yavaş |
| `RemoteTimeMs` | **Replikasyon bekleniyor** (`acks=all`) → follower'lar yavaş |
| `ResponseQueueTimeMs` / `ResponseSendTimeMs` | Ağ tarafı |

> ⭐ **Teşhis kısayolu:** `acks=all` yazma gecikmesinin büyük kısmı `RemoteTimeMs` ise sorun
> **producer'da değil follower'lardadır**.

## 4. JMX'i okumak: üç yol

```bash
# 1) Tek seferlik sorgu (bu setin lab yöntemi)
docker exec kafka-1 /opt/kafka/bin/kafka-run-class.sh org.apache.kafka.tools.JmxTool \
  --jmx-url service:jmx:rmi:///jndi/rmi://localhost:9999/jmxrmi \
  --object-name 'kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions' --one-time

# 2) Sürekli izleme (2 saniyede bir)
docker exec kafka-1 /opt/kafka/bin/kafka-run-class.sh org.apache.kafka.tools.JmxTool \
  --jmx-url service:jmx:rmi:///jndi/rmi://localhost:9999/jmxrmi \
  --object-name 'kafka.server:type=BrokerTopicMetrics,name=BytesInPerSec' --reporting-interval 2000
```

**3) Üretim:** JMX Exporter (Prometheus) java agent olarak broker'a bağlanır; Grafana ile panolanır.
Cluster dışından ölçmek için `kafka-consumer-groups.sh --describe` çıktısını toplayan
lag exporter'ları da yaygındır.

> ⚠️ **Kafka 4.2 (KIP-1100 — [metrik adlandırma düzeltmesi ↗](../00-baslangic/02-kavram-sozlugu.md#kip-1100)) uyarısı:** Metrik adlandırması `kafka.COMPONENT` konvansiyonuna
> uyacak şekilde düzeltildi ve bazı client metrik adları (topic adındaki noktaların alt çizgiye
> çevrildiği varyantlar) **deprecate edildi**. Sürüm yükseltirken panolarını kontrol et.

## 5. Alarm kurma: eşik değil, davranış

| ❌ Kötü alarm | ✅ İyi alarm |
|---|---|
| "Lag > 1000" | "Partition başına maks. lag 10 dakikadır artıyor" |
| "UnderReplicated > 0" (anlık) | "UnderReplicated > 0, **5 dakikadır**" |
| "Disk > %90" | "Disk > %75 **ve** artış hızıyla 6 saatte dolacak" |
| "Rebalance oldu" | "Saatte 10'dan fazla rebalance" |
| "Bir broker düştü" | "**Toplam** ActiveControllerCount != 1" ya da "OfflinePartitions > 0" |

> **Hafıza kancası:** Kafka'da neredeyse hiçbir tekil olay alarm değildir; **süreklilik** alarmdır.
> ISR bir kez daralır ve düzelir — bu normaldir. **5 dakika daralmış kalırsa** anormaldir.

## 6. Uygulama tarafından metrik toplamak (Java)

```java
// Producer/Consumer metriklerini doğrudan koddan oku (2.1'de kullandık)
producer.metrics().forEach((name, metric) -> {
    if (name.group().equals("producer-metrics")
            && Set.of("record-queue-time-avg", "buffer-available-bytes",
                      "record-error-rate", "request-latency-avg").contains(name.name())) {
        registry.gauge("kafka.producer." + name.name(),
                Tags.of("client", name.tags().getOrDefault("client-id", "?")),
                metric, m -> ((Number) m.metricValue()).doubleValue());
    }
});
```

**Uygulamadan mutlaka dışa vurulacak dört metrik:**

| Metrik | Neden |
|---|---|
| `record-error-rate` (producer) | Kalıcı gönderim hataları = **veri kaybı** (2.3) |
| `records-lag-max` (consumer) | Geriden gelme |
| `last-poll-seconds-ago` (consumer) | Rebalance fırtınası **öncesi** uyarı |
| `commit-latency-avg` (consumer) | Coordinator sorunları |

## Sık karıştırılanlar — tek tabloda

| Karışan | Doğrusu | Neden diğeri değil |
|---|---|---|
| Toplam lag ↔ partition başına lag | **Partition başına maksimum** izlenir | Ortalama tek boğulmuş partition'ı gizler |
| Lag (adet) ↔ lag (zaman) | Karar için **zaman** cinsinden daha anlamlı | 50.000 kayıt bazen 2 sn, bazen 2 saat |
| `UnderReplicated` ↔ `UnderMinIsr` | İlki ISR eksik, ikincisi **yazma duruyor** | İkincisi çok daha kritiktir |
| `ActiveControllerCount` broker'da 1 olmalı ↔ toplamda 1 | **Cluster toplamı** 1 | Controller olmayan broker'da 0 normaldir |
| `LocalTimeMs` ↔ `RemoteTimeMs` | İlki disk, ikincisi **replikasyon beklemesi** | `acks=all`'da gecikme genelde Remote'tadır |
| Idle percent yüksek = kötü ↔ iyi | **Yüksek iyidir** (boşta kapasite var) | Düşük = doygunluk |
| Anlık alarm ↔ süreklilik alarmı | Kafka'da **süreklilik** izlenir | Anlık dalgalanma normaldir |

## 🖥 Pratik — cluster'ını JMX'ten oku

> **Amaç:** Kritik metrikleri elle sorgulamak ve arıza anında nereye bakacağını görmek · **Süre:** 20 dk
> **💸 Maliyet:** Yok.

### Adımlar

1. Kritik dörtlüyü oku:
   ```bash
   for m in \
     "kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions" \
     "kafka.server:type=ReplicaManager,name=UnderMinIsrPartitionCount" \
     "kafka.controller:type=KafkaController,name=ActiveControllerCount" \
     "kafka.controller:type=KafkaController,name=OfflinePartitionsCount"; do
     docker exec kafka-1 /opt/kafka/bin/kafka-run-class.sh org.apache.kafka.tools.JmxTool \
       --jmx-url service:jmx:rmi:///jndi/rmi://localhost:9999/jmxrmi \
       --object-name "$m" --one-time 2>/dev/null | tail -1
   done
   ```
2. **`ActiveControllerCount`'u üç broker'da da oku** (kafka-2 ve kafka-3 için komutu tekrarla).
   Kaç tanesi 1 döndürüyor? Bu sayı neden **cluster toplamı** olarak izlenmeli?
3. Doygunluk metriklerini oku:
   ```bash
   docker exec kafka-1 /opt/kafka/bin/kafka-run-class.sh org.apache.kafka.tools.JmxTool \
     --jmx-url service:jmx:rmi:///jndi/rmi://localhost:9999/jmxrmi \
     --object-name 'kafka.server:type=KafkaRequestHandlerPool,name=RequestHandlerAvgIdlePercent' --one-time
   ```
4. **Arızayı yarat ve izle:** Bir broker'ı durdur ve metriği tekrar oku:
   ```bash
   docker stop kafka-3
   docker exec kafka-1 /opt/kafka/bin/kafka-run-class.sh org.apache.kafka.tools.JmxTool \
     --jmx-url service:jmx:rmi:///jndi/rmi://localhost:9999/jmxrmi \
     --object-name 'kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions' --one-time
   docker start kafka-3
   ```
5. **Lag'i partition bazında gör:**
   ```bash
   docker exec kafka-1 /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server kafka-1:19092 \
     --describe --all-groups
   ```
   `LAG` kolonunun **partition başına** verildiğine dikkat et — panolarında da böyle olmalı.
6. **Sürekli izleme:** `--reporting-interval 2000` ile `BytesInPerSec`'i izlerken başka bir
   terminalde 2.1'deki benchmark'ı çalıştır ve grafiğin nasıl hareket ettiğini gör.

## Nasıl karşına çıkar — örnek kalıplar

**Kalıp 1 — Gizlenen darboğaz**
> *"Ortalama lag düşük ama müşteriler gecikme şikâyet ediyor."*
> → Tek bir partition boğulmuş. **Partition başına maks. lag** izle.

**Kalıp 2 — Yanlış alarm**
> *"`UnderReplicatedPartitions` gün içinde defalarca alarm veriyor."*
> → Anlık dalgalanma normaldir. Alarmı **süreye** bağla (5 dakikadır > 0).

**Kalıp 3 — Kritik ayrım**
> *"`UnderReplicated` var ama sistem çalışıyor, aciliyet ne?"*
> → `UnderMinIsrPartitionCount` da > 0 ise `acks=all` yazmalar **reddediliyordur** — kritik.
> Yalnızca UnderReplicated ise dayanıklılık düşmüştür ama yazma sürüyordur.

**Kalıp 4 — Replikasyon teşhisi**
> *"Produce gecikmesi yüksek."* → `TotalTimeMs` bileşenlerine bak. `RemoteTimeMs` yüksekse
> sorun **follower'larda**, `LocalTimeMs` yüksekse **diskte**.

**Kalıp 5 — Erken uyarı**
> *"Rebalance fırtınasını önceden görebilir miyiz?"*
> → `last-poll-seconds-ago` metriğini izle; `max.poll.interval.ms`'in %70'ini geçerse uyar.

**Kalıp 6 — Controller sorusu**
> *"`ActiveControllerCount` 0 gösteriyor, panik mi?"* → O broker controller değilse normaldir.
> **Cluster toplamı** 1 olmalı.

## 60 saniyelik özet

- Alarm dörtlüsü: **ActiveControllerCount (toplam=1)** · **OfflinePartitionsCount (0)** ·
  **UnderReplicatedPartitions (0)** · **UnderMinIsrPartitionCount (0)**.
- `UnderMinIsr` > 0 ⇒ **`acks=all` yazmalar reddediliyor** — UnderReplicated'dan çok daha kritik.
- `ActiveControllerCount` broker başına okunur; **controller olmayanda 0 normaldir**.
- **Lag'i partition başına ve zaman cinsinden izle**; ortalama tek boğulmuş partition'ı gizler.
- `last-poll-seconds-ago` rebalance fırtınasından **önce** uyarır.
- Doygunluk: `RequestHandlerAvgIdlePercent` (→ `num.io.threads`),
  `NetworkProcessorAvgIdlePercent` (→ `num.network.threads`). **Yüksek iyidir.**
- `TotalTimeMs` bileşenleri teşhis eder: `RequestQueue` (kuyruk) · `Local` (disk) ·
  **`Remote` (replikasyon)** · `Response*` (ağ).
- Uygulamadan dışa vur: `record-error-rate` · `records-lag-max` · `last-poll-seconds-ago` ·
  `commit-latency-avg`.
- Alarmları **süreye** bağla; Kafka'da anlık dalgalanma normaldir.
- Kafka 4.2 (KIP-1100) metrik adlarını düzeltti — yükseltmede panolarını kontrol et.
