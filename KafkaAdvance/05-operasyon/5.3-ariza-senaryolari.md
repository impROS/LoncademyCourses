# 5.3 — Arıza senaryoları ve troubleshooting

> **Alan:** Operasyon — ⭐ bu setin en pratik konusu; nöbetteyken açacağın dosya
> **Süre:** ~35 dakika okuma + 30 dakika pratik
> **Test:** [`5.3-test.html`](5.3-test.html) · 15 soru

## Neden bu konu

Önceki 17 konuda mekanizmaları öğrendik. Burada onları **teşhis reflekslerine** çeviriyoruz.
Nöbette olan biri "log segment'in nasıl çalıştığını" düşünmez; **"disk doldu, ne yapıyorum?"** diye sorar.

Bu dosya bir **runbook** gibi yazıldı: her senaryo için belirti → hızlı teşhis → çözüm →
sonradan yapılacak kalıcı düzeltme.

> **Büyük fikir:** Kafka arızalarının %90'ı sekiz kalıptan biridir. Kalıbı tanırsan teşhis
> 5 dakikaya, tanımazsan 5 saate iner.

## 1. ⭐ Teşhis akışı: her zaman aynı üç adım

```
1) KATMAN?      producer  ·  broker/cluster  ·  consumer
2) BELİRTİ?     kayıp · duplicate · yavaşlık · durma · hata mesajı
3) KANIT?       metrik + describe çıktısı + broker logu   (varsayım değil)
```

**Her arızada ilk çalıştırılacak dört komut:**

```bash
# 1) Cluster sağlığı
kafka-metadata-quorum.sh --bootstrap-controller kafka-1:9093 describe --status

# 2) Offline/under-replicated var mı
kafka-topics.sh --bootstrap-server kafka-1:19092 --describe --under-replicated-partitions
kafka-topics.sh --bootstrap-server kafka-1:19092 --describe --unavailable-partitions

# 3) Tüketici tarafı
kafka-consumer-groups.sh --bootstrap-server kafka-1:19092 --describe --all-groups

# 4) Broker logu (son 200 satır, ERROR/WARN)
docker compose -f lab/docker/docker-compose.yml logs --tail 200 kafka-1 | grep -E "ERROR|WARN"
```

## 2. ⭐ Senaryo 1 — Partition offline (`Leader: none`)

**Belirti:** Bazı partition'lara ne yazılabiliyor ne okunabiliyor; `OfflinePartitionsCount > 0`.

**Gerçek lab çıktısı** (replication.factor=1 topic, o replikanın bulunduğu broker durduruldu):

```
Topic: lab-rf1  Partition: 0  Leader: 2     Replicas: 2  Isr: 2  Elr:    LastKnownElr:
Topic: lab-rf1  Partition: 1  Leader: none  Replicas: 3  Isr:    Elr: 3  LastKnownElr: 3
Topic: lab-rf1  Partition: 2  Leader: 1     Replicas: 1  Isr: 1  Elr:    LastKnownElr:

OfflinePartitionsCount = 1
```

`Leader: none`, `Isr:` boş, `Elr: 3` — ELR (1.2) "veri hâlâ 3'te güvenli" diyor.

| Adım | Ne yaparsın |
|---|---|
| Hızlı teşhis | `--describe --unavailable-partitions` ile hangi partition'lar |
| **Çözüm** | Eksik broker'ı **geri getir**. Lider dönünce partition otomatik açılır |
| Broker geri gelmiyorsa | `unclean.leader.election` **son çaredir** ve **veri kaybıdır** (1.2) |
| Kalıcı düzeltme | replication.factor=1 topic bırakma; replication.factor ≥ 3 |

> ⚠️ **Lab'da yakaladığımız ikinci hata:** replication.factor=1 topic broker varsayılanı `min.insync.replicas=2`'yi
> miras aldı. Bu topic **sağlıklıyken bile** `acks=all` ile yazılamaz —
> `replication.factor < min.insync.replicas` **kalıcı bir yapılandırma hatasıdır**.

## 3. ⭐ Senaryo 2 — Disk doldu

**Belirti:** Broker açılmıyor ya da kapanıyor; log'da `No space left on device`; partition'lar offline.

```
Error while writing meta.properties file /var/lib/kafka/data: java.io.IOException: No space left on device
```

| Adım | Ne yaparsın |
|---|---|
| **Yapma** | Log dosyalarını elle **silme** — broker'ın durumu bozulur, veri kaybı olur |
| Hızlı çözüm | En büyük topic'lerde `retention.ms` / `retention.bytes` **düşür**, bekle (`log.retention.check.interval.ms`, 5 dk) |
| Hızlandırma | `segment.ms` düşür ki segmentler dönsün ve silinebilsin (1.4) |
| Alternatif | Gereksiz topic'leri sil; `kafka-delete-records.sh` ile belirli offset öncesini buda |
| Kalıcı | Disk uyarısını **%75**'te kur; tiered storage (1.5); kapasite planı (5.5) |

```bash
# Retention'ı geçici düşür (topic bazında)
kafka-configs.sh --bootstrap-server kafka-1:19092 --entity-type topics --entity-name buyuk-topic \
  --alter --add-config retention.ms=3600000,segment.ms=60000

# Belirli offset öncesini buda (dikkatli!)
echo '{"partitions":[{"topic":"buyuk-topic","partition":0,"offset":1000000}],"version":1}' > /tmp/d.json
kafka-delete-records.sh --bootstrap-server kafka-1:19092 --offset-json-file /tmp/d.json
```

## 4. ⭐ Senaryo 3 — Rebalance fırtınası

**Belirti:** Consumer group ilerlemiyor, log'da sürekli "Request joining group", lag artıyor.

| Sebep | Kanıt | Çözüm |
|---|---|---|
| İşleme çok uzun | `last-poll-seconds-ago` yüksek, `CommitFailedException` | `max.poll.records` ([tek poll’un döndüreceği kayıt sayısı ↗](../00-baslangic/02-kavram-sozlugu.md#maxpollrecords)) düşür (3.1) |
| Pod restart döngüsü | K8s event'leri, OOMKilled ([konteyner bellek limitini aştı ↗](../00-baslangic/02-kavram-sozlugu.md#oom)) | Bellek limiti; `group.instance.id` (3.2) |
| GC duraklaması | GC logları, `session.timeout.ms` ([heartbeat gelmezse ölü sayma süresi ↗](../00-baslangic/02-kavram-sozlugu.md#sessiontimeoutms)) aşımı | Heap ayarı |
| Eager assignor + rolling deploy | Tüm atamalar geri alınıyor | `CooperativeStickyAssignor` ya da `group.protocol=consumer` |
| Assignor uyuşmazlığı | Grup hiç kurulmuyor | Tüm client'larda aynı strateji |

```bash
kafka-consumer-groups.sh --bootstrap-server kafka-1:19092 --describe --group g --state
# STATE: PreparingRebalance / CompletingRebalance'ta takılıysa → fırtına
```

## 5. Senaryo 4-8 — hızlı referans

### Senaryo 4 — Consumer ilerlemiyor ama rebalance yok
| Olası sebep | Kanıt | Çözüm |
|---|---|---|
| **Zehirli kayıt** | `SerializationException`, `position` sabit | Sarmalayıcı deserializer + DLQ ([dead letter queue — ölü mektup topic’i ↗](../00-baslangic/02-kavram-sozlugu.md#dlq)) + `seek` (2.4) |
| **Açık transaction (LSO — [Last Stable Offset — açık transaction sınırı ↗](../00-baslangic/02-kavram-sozlugu.md#lso))** | `read_committed` tüketici, lag var, broker sağlıklı | Açık transaction'ı bul; `transaction.timeout.ms` bekle (4.1) |
| Aşağı akış sistemi yavaş | İşleme süresi metriği | `pause`/`resume`, paralellik (3.1) |
| Partition atanmamış | `--describe` çıktısında `CONSUMER-ID: -` | Consumer sayısı > partition sayısı (3.2) |

### Senaryo 5 — Producer yazamıyor
| Hata | Sebep | Çözüm |
|---|---|---|
| `NotEnoughReplicasException` | ISR ([lidere senkron replikalar kümesi ↗](../00-baslangic/02-kavram-sozlugu.md#isr)) < `min.insync.replicas` ([acks=all için gereken asgari güncel kopya ↗](../00-baslangic/02-kavram-sozlugu.md#mininsyncreplicas)) | Broker'ı geri getir (1.2) |
| `TimeoutException` (retry sonrası) | Genelde yukarıdakinin maskelenmiş hâli | Broker logu + `UnderMinIsr` metriği |
| `RecordTooLargeException` | `max.request.size` / `message.max.bytes` | Üç yerde birden ayarla (2.1) |
| `ProducerFencedException` | Aynı `transactional.id` ([producer’ın kalıcı kimliği ↗](../00-baslangic/02-kavram-sozlugu.md#transactionalid)) başkasında | Producer'ı kapat; id'leri ayır (4.1) |
| `TimeoutException: ... buffer memory` | Tampon dolu (backpressure — [üst akışı bilerek yavaşlatma ↗](../00-baslangic/02-kavram-sozlugu.md#backpressure)) | Aşağı akışa bak; ayarı büyütmek erteler (2.1) |

### Senaryo 6 — Bir broker CPU/disk'i yiyor
| Sebep | Kanıt | Çözüm |
|---|---|---|
| Lider dengesizliği | `--describe` çıktısında liderler bir broker'da toplanmış | `kafka-leader-election.sh --election-type preferred` |
| Sıcak partition (key skew) | Partition başına `BytesInPerSec` | Key tasarımını gözden geçir (5.5) |
| TLS + sıfır kopya ([veriyi çekirdekten doğrudan sokete aktarma ↗](../00-baslangic/02-kavram-sozlugu.md#sıfır-kopya)) kaybı | TLS açık, CPU yüksek | Beklenen; kapasite planla (1.1, 5.4) |
| Partition sayısı dengesiz | `kafka-reassign-partitions.sh` gerekli | Yeniden dağıtım |

### Senaryo 7 — Cluster metadata işlemleri durdu
> Topic oluşturulamıyor ama okuma/yazma sürüyor → **controller quorum'u (karar için gereken salt çoğunluk) çoğunluğu kaybetti** (1.3).
> `kafka-metadata-quorum.sh describe --status` ile voter'ları (oy veren controller düğümü) kontrol et; eksik node'ları geri getir.

### Senaryo 8 — Veri "kayboldu"
> Sırayla bak: `acks` ([kaç kopyanın onayı beklenir ↗](../00-baslangic/02-kavram-sozlugu.md#acks)) → `min.insync.replicas` (replication.factor ile karşılaştır) → `unclean.leader.election.enable` ([ISR dışı replika lider olabilsin mi ↗](../00-baslangic/02-kavram-sozlugu.md#uncleanleaderelectionenable))
> → producer **callback'inde hata yutuluyor mu** (2.3) → tüketicide **önce commit** deseni var mı (3.3).
> Bu beşinin dışında Kafka'nın veri kaybettiği bir senaryo pratikte çok nadirdir.

## Sık karıştırılanlar — tek tabloda

| Karışan | Doğrusu | Neden diğeri değil |
|---|---|---|
| Offline partition ↔ under-replicated | Offline = **lider yok, erişilemez**; under-replicated = kopya eksik ama çalışıyor | Aciliyet farkı büyük |
| Disk dolunca log silmek ↔ retention düşürmek | **Retention düşür**, broker kendi silsin | Elle silme broker durumunu bozar |
| Rebalance fırtınası ↔ yavaş consumer | Fırtınada grup **hiç ilerlemez** | Yavaşlıkta lag artar ama iş görülür |
| `TimeoutException` ↔ ağ sorunu | Çoğu zaman `NotEnoughReplicas`'ın maskelenmiş hâli | Broker logunu oku (1.2) |
| `unclean.leader.election` ↔ kurtarma | **Veri kaybını kabul etmek**tir | Önce broker'ı geri getirmeyi dene |
| Lag var ↔ consumer yavaş | Açık transaction (LSO) da lag üretir | `read_committed` + açık tx (4.1) |
| Metadata durdu ↔ cluster öldü | Broker'lar okuma/yazmaya devam edebilir | Quorum kaybı **metadata yazmayı** durdurur |

## Nasıl karşına çıkar — örnek kalıplar

**Kalıp 1 — Acil müdahale sırası**
> *"Partition'lar offline, ne yapalım?"* → Önce **eksik broker'ı geri getir**.
> `unclean.leader.election` son çare ve veri kaybıdır.

**Kalıp 2 — Disk paniği**
> *"Disk %98, log dosyalarını silelim mi?"* → **Hayır.** Retention'ı düşür, `segment.ms`'i düşür,
> broker'ın kendi temizlemesini bekle.

**Kalıp 3 — Yanlış yapılandırma**
> *"replication.factor=1 topic'e `acks=all` ile yazamıyoruz."* → Broker varsayılanı `min.insync.replicas=2`
> miras alınmış. **replication.factor < min.insync.replicas** kalıcı hatadır.

**Kalıp 4 — Maskelenmiş hata**
> *"Sadece `TimeoutException` görüyoruz."* → Broker logunu ve `UnderMinIsrPartitionCount`'u kontrol et.

**Kalıp 5 — Sinsi lag**
> *"Consumer ilerlemiyor, rebalance yok, broker sağlıklı."* → Zehirli kayıt (2.4) ya da
> açık transaction (LSO, 4.1).

**Kalıp 6 — Yanlış katman**
> *"Bir broker CPU'yu yiyor, cluster'ı büyütelim."* → Önce **lider dengesizliği** ve
> **sıcak key** ihtimaline bak; `preferred` lider seçimi çoğu zaman yeter.

## 60 saniyelik özet

- Teşhis üç adım: **katman → belirti → kanıt**. Varsayımla değil metrik/çıktı/log ile ilerle.
- İlk dört komut: quorum status · `--under-replicated-partitions` / `--unavailable-partitions` ·
  `consumer-groups --describe` · broker logu.
- **Offline partition** = `Leader: none`; çözüm broker'ı geri getirmek. `unclean` = **veri kaybı**.
- **Disk dolduğunda log dosyalarını elle silme**; `retention.ms` + `segment.ms` düşür.
- **replication.factor < `min.insync.replicas`** kalıcı bir yapılandırma hatasıdır (lab'da replication.factor=1 + min.insync.replicas=2 gördük).
- **Rebalance fırtınası**: önce `max.poll.records`; sonra `group.instance.id`, cooperative/KIP-848.
- **İlerlemeyen consumer + rebalance yok** = zehirli kayıt ya da açık transaction (LSO).
- **`TimeoutException`** çoğu zaman `NotEnoughReplicas`'ın maskelenmiş hâlidir.
- **Metadata durması** quorum kaybıdır; okuma/yazma bir süre devam edebilir.
- "Veri kayboldu" beşlisi: `acks` · `min.insync.replicas` · `unclean.leader.election` ·
  **producer callback** · **commit sırası**.
